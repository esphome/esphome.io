Every month ESPHome ships a release like this one, so you can learn about new features, fixes, and other changes worth knowing about before you update.

## Short on time? Here's the quick version

Here's the plain-language rundown for anyone short on time or newer to ESPHome; the full technical post continues below for anyone who wants it.

**Action needed if you use any of these:**

- **Lights with an `initial_state:`** now actually respect it at boot, so if you had a light configured to come up on but it was quietly staying off, double-check the behavior is what you want after updating.
- **The `codec_support_enabled` option on `speaker` media players is gone;** remove it from your config and set the pipeline `format:` to `NONE` to keep the old behavior, otherwise the config will no longer validate.
- **IR climate devices with `supports_heat: false` or `supports_cool: false`** no longer offer the combined heat/cool auto mode by default - add `supports_heat_cool: true` to bring it back if you were relying on it.

**New features:** Updates install about a third smaller and proportionally faster on every platform ESPHome supports, and ESP8266 builds are considerably quicker end-to-end, including on recent Apple Silicon Macs that no longer need Rosetta.

**Also in this release:** 20 new components (including Wi-Fi motion sensing, a persistent counter, a new CO2 sensor, USB-UART bridging and TCP-UART), broader Zigbee cluster coverage, live light transition reporting, CSS color names in light actions, and a long list of smaller fixes and improvements.

If you're running a typical config, there's nothing else you need to look at before updating - aside from the items above, your setup should carry over cleanly.

If you're running custom lambdas, external components, or a non-standard config, or you just want the full technical detail, keep reading below for the full release overview and feature writeups.

## Release overview

{/* RELEASE_OVERVIEW_START */}
ESPHome 2026.10.0 lands two platform-wide defaults that touch most of the fleet: the native ESP8266
Arduino toolchain is now the default build path, retiring Rosetta on Apple Silicon and cutting cold
compile time nearly in half, and OTA uploads are compressed on ESP32, RP2040, LibreTiny and host
through a new deflate decoder, so updates ship about a third fewer bytes and finish proportionally
faster on slow or lossy links. The native API's protobuf and controller-dispatch hot paths got
another round of per-byte and per-instruction optimizations, 20+ field-packing PRs and a sweep
moving codegen data from heap and RAM into flash tables trim RAM across every build, and the
`register_apply_action` and `sub_*` codegen helpers remove hundreds of boilerplate C++ classes and
Python lines across more than 150 components with no YAML changes. ESP-IDF builds now run `cmake`
and `ninja` directly instead of through `idf.py`, and a `--skip-bootloader` flag plus mbedTLS and
tool-startup trims save several more seconds per compile on Home Assistant Green class hardware. On
top of that, 20 new components land, including Wi-Fi CSI motion sensing, USB-UART bridges with mux
and tap seams, TCP-UART and UART-TCP, SPI Ethernet on KSZ8851SNL, a persistent counter sensor and
a Sensirion STCC4 CO2 sensor, alongside a device-side Home Assistant onboarding wizard, outgoing
API connections for NAT-ed devices, broader Zigbee cluster coverage and new light transition,
color, resume-effect and e-paper features.
{/* RELEASE_OVERVIEW_END */}

## Upgrade checklist

{/* UPGRADE_CHECKLIST_START */}
- If you have ESP8266 devices, expect the first compile to be a clean build on the new native `arduino` toolchain;
  set `toolchain: platformio` under `esp8266:` to keep the old path (and plan to migrate before 2027.4.0).
- If you set `restore_mode:` on a `light` with `initial_state: {state: on/off}`, verify the boot state is what you
  want - lights that previously booted off against your `initial_state` will now follow it.
- If you set `codec_support_enabled:` on a `speaker` media player, remove it and switch the pipeline `format:` to
  `NONE` for the old `all` behaviour; configs that still carry the key now fail validation.
- If you rely on a `speaker` or `speaker_source` media player muting itself at volume zero (or firing `on_mute` /
  `on_unmute` from a volume change), update your automations - volume and mute are now independent.
- If you use `climate_ir` platforms with `supports_heat: false` or `supports_cool: false` and want to keep the
  `heat_cool` auto mode, add `supports_heat_cool: true`.
- If you set `buffer_size:` on `remote_receiver` for ESP8266, RP2040, LibreTiny, ESP32-C2 or ESP32-C61, multiply the
  value by 4 to keep the same number of buffered pulses.
- If you have `usb_uart` entries that could match the same USB device (overlapping VID/PID), split them with
  `manufacturer` and `product` filters - overlapping entries are now rejected at validation.
- If you use `epaper_spi` with saturated pure green or magenta drawn by RGB value, review the output; monochrome
  conversion now uses perceived luminance. Also drop `full_update_every` above 1 on panels without partial refresh
  and add `psram:` for `seeed-reterminal-sticky`.
- If you have a `sendspin` switch, add `type: enabled` to each entry.
- If you build for the `host` platform, remove unsupported `platformio_options` keys and rewrite any
  separate-argument `build_flags` (such as `-include pre.h`) as a single entry; Windows host builds are no longer
  supported.
- If you use `homeassistant.action` with more than 255 data/variable keys per action, split it - the config is now
  rejected at validation.
- If you write lambdas that read `tag` after a `delay` in `on_tag` / `on_tag_removed`, note that `tag` is now
  passed by reference; existing read-only uses continue to work, but code that modified a local copy of the tag now
  modifies the shared reference.
{/* UPGRADE_CHECKLIST_END */}

## ESP8266 native toolchain by default

The native Arduino toolchain foundation that landed dormant in 2026.9.0 is now the default for every
ESP8266 build. [@bdraco](https://github.com/bdraco) finished the stack with the compile driver and
dispatch layer ([#18539](https://github.com/esphome/esphome/pull/18539)), ESPHome-built xtensa gcc
10.3 archives for Linux x86_64/arm64, macOS x86_64/arm64 and Windows x86_64 served from
[esphome-libs/xtensa-lx106-elf-toolchain](https://github.com/esphome-libs/xtensa-lx106-elf-toolchain)
instead of the registry package ([#19849](https://github.com/esphome/esphome/pull/19849)), and
flipped the default to `toolchain: arduino` in
[#19886](https://github.com/esphome/esphome/pull/19886). The CI matrix now compiles every ESP8266
component test the same way ([#19714](https://github.com/esphome/esphome/pull/19714),
[#19740](https://github.com/esphome/esphome/pull/19740)).

- **Faster builds end-to-end** - on an M5 Max against the same config an `esphome compile` runs in
  9.2s cold instead of 17.8s, a warm-ccache rebuild in 2.8s instead of 7.6s, a no-op rebuild in 0.4s
  instead of 2.2s, and a one-line edit in 9.6s instead of 20.7s.
- **Apple Silicon without Rosetta** - the registry package had no arm64 macOS build, so ESP8266
  builds on recent Macs needed Rosetta 2, which Apple ends with macOS 28. The ESPHome-built archives
  are native on every supported host.
- **ESP8266 progress in Device Builder** - the native build runs through ninja, so its `[N/M]`
  progress counters feed the device builder a compile percentage the way ESP-IDF builds already do.
- **Opt-out available, deprecated** - a custom framework `source`, a framework version other than
  3.1.2, an unlisted board or an unsupported host still work with `toolchain: platformio`. The
  PlatformIO path warns on validation and goes away in 2027.4.0.

Roughly 40% of ESPHome devices run on ESP8266, so the change touches a large slice of the fleet;
the first build after upgrading is a clean build because the build directory's toolchain changed.

## Compressed OTA uploads on ESP32, RP2040, LibreTiny and host

[@bdraco](https://github.com/bdraco) extended compressed OTA, which the ESP8266 already had via its
gzip-aware bootloader, to every other platform ESPHome supports
([#19037](https://github.com/esphome/esphome/pull/19037)). RP2040 takes the same gzip path through
the Arduino Pico stub. ESP32, LibreTiny and host inflate a raw deflate stream through a 4 KB window
as it arrives, so an image goes over the network about one third smaller than before.

- **Automatic negotiation** - a client bit and a server bit opt in; old clients and old firmware
  never see it, so pre-2026.10.0 devices update exactly as before.
- **Covered by the digest** - the client sends the inflated image's MD5, so the integrity check
  covers the decoder.
- **Big win on slow or lossy links** - ESP32-C6 OpenThread, encrypted WiFi with 15% packet loss and
  any mesh-hop or VPN upload is transfer-bound; measured on an ESP32 at 15% simulated loss, upload
  time drops from 317/113s to 74/67s.
- **Allocation-safe** - the 4.9 KB decoder session is allocated through `RAMAllocator::make_unique`
  so a heap-exhausted device falls back to an uncompressed upload instead of rebooting.

The flash cost is about 2 KB on ESP32 and under 100 bytes on ESP8266 and RP2040 for the negotiation
glue.

## API protobuf throughput and controller dispatch

A sustained push on the native API's hot paths continued through this release.
[@bdraco](https://github.com/bdraco) collapsed the three protobuf decode virtuals into one and
removed the vtable from decode ([#19016](https://github.com/esphome/esphome/pull/19016),
[#19029](https://github.com/esphome/esphome/pull/19029)), made generated encode and size entry
points type-erased ([#19015](https://github.com/esphome/esphome/pull/19015)), passed the encode
cursor by value through the protobuf helpers so it stays in a register
([#19014](https://github.com/esphome/esphome/pull/19014)), counted packed varints a machine word at
a time ([#20122](https://github.com/esphome/esphome/pull/20122)), decoded base64 in a single pass
([#20123](https://github.com/esphome/esphome/pull/20123)), and kept the write cursor in a register
while emitting sub-message tags inline ([#20124](https://github.com/esphome/esphome/pull/20124)).

A separate change dispatches controller updates through generated direct calls instead of a runtime
registry: `APIServer` and `WebServer` drop the `Controller` base class and the state-publish path
goes from 25 instructions with 8 loads and 2 indirect calls to 10 instructions with 2 loads and
direct calls only, costing 256 B less flash and 24 B less RAM on a typical ESP32 build
([#19588](https://github.com/esphome/esphome/pull/19588)). The web server also builds state
documents in a stack arena and sends events straight from the caller's buffers so a state event
does no heap allocation at all ([#19376](https://github.com/esphome/esphome/pull/19376),
[#19383](https://github.com/esphome/esphome/pull/19383)).

External components that subclass `Controller` or hand-write a non-const `AudioFile *` need small
updates; the migration notes are in each PR.

## Memory optimizations across every build

[@bdraco](https://github.com/bdraco) led a tree-wide sweep to shrink per-instance structures and
move constant codegen data out of RAM.

- **Field packing** - roughly twenty PRs grouped single-byte flags next to other byte fields on
  speaker, mixer, i2s_audio, voice_assistant, microphone, sendspin, template, ledc, rtttl, ld2450,
  remote_receiver, esp32_ble, improv_ble, wifi and more
  ([#20135](https://github.com/esphome/esphome/pull/20135) through
  [#20152](https://github.com/esphome/esphome/pull/20152)), reclaiming three bytes of padding at a
  time across many instances.
- **Empty-base packing** - `[[no_unique_address]]` lets the empty `Scheduler` mutex, empty script
  argument tuple, empty template unused members and the empty WiFi `pending_` flags struct take no
  space on single-threaded platforms ([#20139](https://github.com/esphome/esphome/pull/20139),
  [#20140](https://github.com/esphome/esphome/pull/20140),
  [#20141](https://github.com/esphome/esphome/pull/20141),
  [#20142](https://github.com/esphome/esphome/pull/20142)); `App` drops from 156 to 152 bytes on
  ESP8266.
- **Light state 12 bytes smaller** - the effect index became a `uint16_t` sharing a word with the
  flags, the gamma factor rode along in the flash lookup table, and the flash transition length
  only compiles in when a light sets `flash_transition_length`
  ([#19711](https://github.com/esphome/esphome/pull/19711)). `LightState` goes from 180 to 168
  bytes.
- **StaticVector and FreeRTOS handles embedded in place** - the ring buffer, FreeRTOS queue, static
  task and ESP32 logger buffer now use the static structure as their own handle instead of
  allocating one next to it ([#20129](https://github.com/esphome/esphome/pull/20129),
  [#20133](https://github.com/esphome/esphome/pull/20133),
  [#20134](https://github.com/esphome/esphome/pull/20134)).
- **Codegen data in flash** - audio files, display init sequences, select options, font glyphs, RC
  switch protocols, allowed origins, UDP addresses, BLE MAC filter lists, matrix keypad keys, Home
  Assistant action fields and select.is option lists are now `constexpr` tables in flash instead of
  heap or RAM objects built in `setup()` ([#20072](https://github.com/esphome/esphome/pull/20072),
  [#20079](https://github.com/esphome/esphome/pull/20079),
  [#20081](https://github.com/esphome/esphome/pull/20081),
  [#20085](https://github.com/esphome/esphome/pull/20085),
  [#20086](https://github.com/esphome/esphome/pull/20086),
  [#20088](https://github.com/esphome/esphome/pull/20088),
  [#20089](https://github.com/esphome/esphome/pull/20089),
  [#20090](https://github.com/esphome/esphome/pull/20090),
  [#20091](https://github.com/esphome/esphome/pull/20091),
  [#20108](https://github.com/esphome/esphome/pull/20108),
  [#20110](https://github.com/esphome/esphome/pull/20110),
  [#20117](https://github.com/esphome/esphome/pull/20117),
  [#20237](https://github.com/esphome/esphome/pull/20237)); the Voice PE config saves 192 B of RAM
  and 272 B of flash from the audio files change alone.
- **Header inlining** - trivial single-store setters moved into headers on template, bme280_base,
  bme680, bmp280_base, mqtt_subscribe, tsl2561, tsl2591, esp32_camera, web_server, waveshare_epaper,
  bang_bang, graphical_display_menu, adc, thermostat, openthread, st7789v, max44009, sds011, haier,
  lc709203f ([#19278](https://github.com/esphome/esphome/pull/19278) through
  [#19299](https://github.com/esphome/esphome/pull/19299)) and setters that pass defaults are
  skipped at codegen on api, template, uart and version
  ([#19227](https://github.com/esphome/esphome/pull/19227),
  [#19232](https://github.com/esphome/esphome/pull/19232),
  [#20066](https://github.com/esphome/esphome/pull/20066),
  [#20067](https://github.com/esphome/esphome/pull/20067),
  [#20069](https://github.com/esphome/esphome/pull/20069)).
- **ESP8266 log tags and flash strings** - every `ESPHOME_LOG_TAG` on ESP8266 now rides in flash
  ([#20290](https://github.com/esphome/esphome/pull/20290),
  [#19574](https://github.com/esphome/esphome/pull/19574),
  [#19578](https://github.com/esphome/esphome/pull/19578)) and the long-inert
  `esp8266_store_log_strings_in_flash` option that forced them into RAM is deprecated and ignored
  ([#19577](https://github.com/esphome/esphome/pull/19577)).
- **ESP32 unused subsystems trimmed** - a `flash_chip` option under `esp32: framework: advanced:`
  drops the unused flash-vendor driver tables, saving up to 5 KB of RAM and image on an ESP32-S3
  with octal flash ([#19217](https://github.com/esphome/esphome/pull/19217)), and
  `nvs_cache_in_psram` moves ESP-IDF's internal NVS page cache into PSRAM for an extra ~10 KB of

  ([#19378](https://github.com/esphome/esphome/pull/19378)).

## Codegen architecture: register_apply_action

[@bdraco](https://github.com/bdraco) finished one of the largest coordinated refactors in recent
memory. `register_apply_action` and `register_apply_condition` turn an action or condition that
only forwards config values to its parent into a field table with no C++ class and no builder, with
constants and inline lambdas baked into one stateless function
([#19469](https://github.com/esphome/esphome/pull/19469),
[#19655](https://github.com/esphome/esphome/pull/19655)).

Over 80 components moved onto it in this release, covering actions and conditions on cover, fan,
climate, light, switch, valve, lock, number, text, select, event, media_player, speaker,
voice_assistant, mqtt, globals, update, ledc, esp32_ble_tracker, alarm_control_panel, rtttl,

instantiated by codegen and never reachable from user lambdas, so no YAML changes.

## ESP-IDF build speed

[@bdraco](https://github.com/bdraco) replaced the `idf.py` wrapper with direct `cmake` and `ninja`
calls, matching the native ESP8266 and host paths
([#19871](https://github.com/esphome/esphome/pull/19871)). The firmware is byte-identical across
nine scenarios on ESP-IDF 5.5.5 and 6.1.0 and a CI check runs the real `idf.py` on a freshly built
tree so an IDF bump cannot drift unnoticed. The win is Python startup and the removed second
`ninja all`: about 5 seconds saved per build on a Home Assistant Green.

Several supporting pieces compound the saving.

- **`--skip-bootloader` flag** for OTA-only builds disables the bootloader sub-build when the
  update will never deliver one, saving 7.5 s per compile on a warm ccache on an M5 Max and
  proportionally more on Green-class hardware ([#19925](https://github.com/esphome/esphome/pull/19925)).
- **Build-and-size in one ninja run** instead of two
  ([#19997](https://github.com/esphome/esphome/pull/19997)) and the `json2` size data emitted so
  the link edge is not blocked ([#18848](https://github.com/esphome/esphome/pull/18848)).
- **ESP-IDF tool paths resolved once per build** and the IDF version read in-process instead of
  starting `idf_tools` ([#19996](https://github.com/esphome/esphome/pull/19996),
  [#19998](https://github.com/esphome/esphome/pull/19998)).
- **mbedTLS trimmed** to the client-only defaults needed by ESPHome's HTTPS and MQTT paths, and
  disabled entirely when no component needs crypto
  ([#18877](https://github.com/esphome/esphome/pull/18877),
  [#19088](https://github.com/esphome/esphome/pull/19088)).
- **nRF52 shared ccache** between devices and native-toolchain cache settings
  ([#20027](https://github.com/esphome/esphome/pull/20027),
  [#20028](https://github.com/esphome/esphome/pull/20028)).

## Native API outgoing connections

[@bdraco](https://github.com/bdraco) added `outgoing_connection` under `api:` so the device opens
the native API connection itself instead of waiting to be reached
([#18919](https://github.com/esphome/esphome/pull/18919)). With no `host:` the device remembers the
last dial-back client and reconnects when that client stops reaching it; with `host:` set the
device always dials out, which covers a peer behind NAT or on a routed segment it cannot reach
inbound.

- **Noise only** - the option requires `encryption:` because the connection can leave the LAN and
  the shared key is the only trustworthy way to verify the peer.
- **Protocol unchanged** - the device stays the Noise responder; it only sends its server hello
  first so the peer can pick the key by name and MAC.
- **Deep-sleep aware** - deep-sleep builds skip the connect delay and dial as soon as the network
  is up.

The cost on an ESP32 is 32 B of RAM with `outgoing_connection` plus a `host`, 48 B when learning
the target. aioesphomeapi 46.4.0 and Home Assistant core already know how to answer.

## Setup wizard for Home Assistant onboarding

[@jesserockz](https://github.com/jesserockz) added a device-side setup wizard that Home Assistant
can show during onboarding ([#19966](https://github.com/esphome/esphome/pull/19966)). A `wizard:`
block under `api:` describes a series of pages with device entities to highlight (an enable
switch, for example) and inputs that pick Home Assistant entities the device needs. Inputs can be
linked to a `homeassistant`-platform entity so the device subscribes to it automatically, or stand
alone as a plain entity id a lambda can use.

The wizard is fixed at build time and compressed with zstd on the Python side, so the device
shippers one blob out of flash and the format can grow without new proto fields. On an ESP32-IDF
build a single-switch wizard adds about 0.4 KB of flash; a config with no wizard adds nothing. The
Home Assistant integration PR follows.

## Light transition state publishing and color names

[@nohat](https://github.com/nohat) added an opt-in `transition_state_publish_interval` on every
light so Home Assistant and MQTT subscribers see the live value during a fade or flash instead of
just the start and end ([#11968](https://github.com/esphome/esphome/pull/11968)). Values below 150
ms are rejected; 200 to 250 ms is a good value. The build pays nothing unless at least one light
sets the option, and each light grows by 8 bytes of RAM when the option is enabled. This also lays
the groundwork for hold-to-dim.

Two other light-side quality-of-life improvements landed from
[@clydebarrow](https://github.com/clydebarrow): CSS color names and `0xRRGGBB` values anywhere a
light state is specified, including strobe and `addressable_color_wipe`
([#19712](https://github.com/esphome/esphome/pull/19712),
[#19874](https://github.com/esphome/esphome/pull/19874)); and `resume_effect:` from
[@TheRealChriAnd](https://github.com/TheRealChriAnd) that resumes the running effect after a plain
turn-off / turn-on ([#17791](https://github.com/esphome/esphome/pull/17791)). `restore_mode` is
replaced by a more expressive `restore_state` that can leave, invert or force a specific value per
property, with a warning when a legacy `restore_mode` would silently discard an explicit
`initial_state` ([#18997](https://github.com/esphome/esphome/pull/18997)).

## Host platform builds natively

[@jesserockz](https://github.com/jesserockz) moved the host platform off PlatformIO onto ninja and
the machine's own compiler, matching how ESP32 and ESP8266 already build
([#19214](https://github.com/esphome/esphome/pull/19214)). Compilers are picked from `PATH`
(`g++`/`gcc` first, then clang, honouring `CC`/`CXX`), ccache is used when present, and libraries
go through the shared converter into archives. Build-flag routing follows SCons semantics, and
`cg.set_cpp_standard` replaces the old `-std=gnu++20` build flag so C sources never see a C++
standard. Measured on an M5 Max against the same host config and the same 128 objects, a cold
build takes 2.4 s instead of 3.9 s, a no-op rebuild 0.3 s instead of 1.2 to 1.4 s, and a clean
build with a warm ccache 0.5 s instead of 4.0 s.

## USB bridging, mux and serial proxy taps

A connected effort landed around sharing physical ports between a USB host, an on-device component
and remote API consumers. Starting from [@kbx81](https://github.com/kbx81)'s new
[bridge](/components/bridge) component with its first `cdc_acm_uart` platform
([#11689](https://github.com/esphome/esphome/pull/11689)), the ESP32-S2/S3/P4 can present as a
USB-to-UART bridge with dynamic line coding, DTR/RTS output, and clean `pause()`/`resume()` for
sharing the UART with on-device code. The new [uart_mux](/components/uart_mux) component
([#19066](https://github.com/esphome/esphome/pull/19066)) routes a UART to either the bridge or a
local consumer like `zwave_proxy`, driven by `tinyusb` `on_mount` / `on_unmount` automations added
in [#19067](https://github.com/esphome/esphome/pull/19067).

Alongside it, `serial_proxy` grew a protocol-agnostic tap seam and port mode so Home Assistant can
flash through a port that normally carries a protocol
([#18955](https://github.com/esphome/esphome/pull/18955)) and a `USB_SERIAL` port type plus a
`SerialProxyIdentity` message so clients can target a specific USB device even when the topology
changes ([#19308](https://github.com/esphome/esphome/pull/19308), by
[@puddly](https://github.com/puddly)). `usb_uart` gained descriptor filters for `iManufacturer` and
`iProduct` for devices that share VID/PID ([#19095](https://github.com/esphome/esphome/pull/19095))
and a `claim_comm_interface: false` option that frees a USB host hardware channel per device on
channel-poor hosts like the ESP32-S3
([#18969](https://github.com/esphome/esphome/pull/18969)).

## Signed OTA mDNS and plaintext migration lane

[@kbx81](https://github.com/kbx81) made devices built with `signed_ota_verification` advertise an
`ota_signed=1` TXT record on `_esphomelib._tcp`, so a discovery client like Device Builder knows up
front it needs a trusted key before compiling anything
([#19407](https://github.com/esphome/esphome/pull/19407)). To bridge the long tail of devices that
cannot encrypt yet, [@bdraco](https://github.com/bdraco) added `allow_plaintext_upload: true` under

in 2027.3.0; the uploader logs that the install went plaintext and tells the user to remove the
option once the device is seen encrypting ([#19396](https://github.com/esphome/esphome/pull/19396)).

## Breaking changes

{/* BREAKING_CHANGES_USERS_START */}
### Platform changes

- **Host**: The `host` platform now builds natively with ninja instead of PlatformIO. Keys under
  `esphome.platformio_options` other than `build_unflags`, `lib_deps` and `lib_ignore` are ignored with a warning, and
  `platformio_options.build_flags` still works but is deprecated in favour of `esphome.build_flags`. Flags that take a
  separate argument (such as `-include pre.h`) must be written as a single `build_flags` entry; `--toolchain
  platformio` is rejected on host. Windows is refused because the host sources use POSIX interfaces.
  [#19214](https://github.com/esphome/esphome/pull/19214)
- **ESP8266**: The native `arduino` toolchain is now the default. To keep the previous behaviour, set `toolchain:
  platformio` under `esp8266:` or pass `--toolchain platformio` on the command line. A custom framework `source`, a
  framework version other than `3.1.2`, or an unlisted board still requires the PlatformIO toolchain, which now emits
  a deprecation warning and will be removed in 2027.4.0. [#19886](https://github.com/esphome/esphome/pull/19886)

### Component changes

- **Light**: Added a new `restore_state:` option that replaces `restore_mode:`. The old key still works and remains
  valid, but is now deprecated. A light configured with `initial_state: {state: on}` and no explicit `restore_mode:`
  now actually boots on, instead of being silently forced off by the previous `ALWAYS_OFF` default. Monochrome colour
  mixing for `on`/`off` state now prefers `ON`/`OFF` tokens.
  [#18997](https://github.com/esphome/esphome/pull/18997)
- **Speaker**: Removed the deprecated `codec_support_enabled` option from the `speaker` media player. Configs that
  still set the key now fail validation; use the pipeline `format:` setting, with `format: NONE` replacing the old
  `all` mode. [#19074](https://github.com/esphome/esphome/pull/19074)
- **Speaker**: In the `speaker` media player, volume and mute are now independent. Setting the volume to zero is
  silent but no longer reports the player as muted, `on_mute` / `on_unmute` no longer fire from volume changes, and
  changing the volume while muted keeps the mute on. [#19307](https://github.com/esphome/esphome/pull/19307)
- **Speaker Source**: The same volume/mute independence now applies to the `speaker_source` media player: a saved
  volume of zero no longer forces mute on at boot, and `on_mute` / `on_unmute` no longer fire from volume changes.
  [#18412](https://github.com/esphome/esphome/pull/18412)
- **Serial Proxy**: Added a tap interface and port mode (`RAW` / `PROTOCOL`), controlled only by the live subscriber
  via a new API request. Every port write, configure, modem-pin, flush and mode operation now requires being the
  current subscriber. [#18955](https://github.com/esphome/esphome/pull/18955)
- **USB Host / USB UART**: Added `manufacturer` and `product` descriptor filters for the `usb_uart` platform.
  Validation is stricter: two `usb_uart` entries can no longer match the same USB device, so configurations with
  overlapping VID/PID entries now fail at validation time.
  [#19095](https://github.com/esphome/esphome/pull/19095)
- **Remote Receiver**: On ESP32 with the current RMT driver, the ring buffer is now sized from `receive_symbols` by
  default (four slots, around 3136 bytes at the defaults) instead of a fixed `10kb`. Explicit `buffer_size:` values
  still override it. [#19100](https://github.com/esphome/esphome/pull/19100)
- **Remote Receiver**: On ESP8266, RP2040, LibreTiny, ESP32-C2 and ESP32-C61, `buffer_size:` is now interpreted as
  bytes rather than entries, matching the validator. The default moves from `1000b` to `4000b` so the number of
  buffered pulses stays the same; an explicit value must be multiplied by 4 to keep the same pulse count.
  [#19101](https://github.com/esphome/esphome/pull/19101)
- **E-Paper SPI**: Monochrome colour conversion now uses Rec.601 luma, so some saturated colours render differently
  (pure green `(0,255,0)` was black and is now white; magenta `(255,0,255)` was white and is now black). Grays,
  black, white, red, blue, yellow and cyan are unchanged. `full_update_every` above 1 is rejected on panels without
  partial refresh, `seeed-reterminal-sticky` now requires `psram:`, SSD1677 panels with partial refresh allocate a
  second frame buffer, and `seeed-reterminal-sticky-gray4` requires a width that is a multiple of 8 when
  `dimensions:` is overridden. [#19213](https://github.com/esphome/esphome/pull/19213)
- **Climate IR**: `CLIMATE_MODE_HEAT_COOL` is no longer advertised when either `supports_heat:` or `supports_cool:`
  is false. A new `supports_heat_cool:` key overrides the default when a device does not follow the rule. Platforms
  built on `climate_ir` (except `mitsubishi`, which is unchanged, and `gree`, which changes only for
  `supports_cool: false`) no longer offer the `heat_cool` mode in those configurations.
  [#19483](https://github.com/esphome/esphome/pull/19483)
- **Hoermann HCP**: Commands are now sent once per status answer, following the Hoermann bus accessory. Open, close,
  set position, vent and half-open requests issued while the door is already moving now only stop the door, so a
  burst of commands can no longer reverse or restart it at speed. The lamp is tracked as an absolute state.
  [#19765](https://github.com/esphome/esphome/pull/19765)
- **Sendspin**: The `sendspin` switch platform now requires a `type:` option. The only supported value today is
  `enabled`. [#20189](https://github.com/esphome/esphome/pull/20189)
{/* BREAKING_CHANGES_USERS_END */}

### Undocumented API changes

{/* UNDOCUMENTED_API_CHANGES_START */}
These are C++ API changes that are not covered by the formal breaking change policy because the methods are
internal or undocumented. Lambda users and external component authors may still want to be aware of them.

### Removed deprecated members

- **Sensor**: The public `raw_state` member is gone. Use `get_raw_state()` instead.
  [#19077](https://github.com/esphome/esphome/pull/19077)

  ```cpp
  // Before
  float v = id(my_sensor).raw_state;
  // After
  float v = id(my_sensor).get_raw_state();
  ```

- **Modbus Controller**: The forwarding shims in the `modbus_controller` namespace for `value_type_is_float()`,
  `modbus_register_read_function()`, `modbus_register_write_function()`, `c_to_hex()`, the `*_from_hex_str()`
  family, the vector overload of `get_data()`, `mask_and_shift_by_rightbit()`, `number_to_payload()`,
  `payload_to_number()` and `float_to_payload()` are removed. The replacements live in `modbus::helpers`. The span
  overloads and `coil_from_vector()` are kept until 2027.2.0.
  [#19076](https://github.com/esphome/esphome/pull/19076)

  ```cpp
  // Before, in a lambda
  modbus_controller::c_to_hex('A');
  // After
  modbus::helpers::c_to_hex('A');
  ```

### Remote base protocol methods are no longer virtual

- **Remote Base**: `encode`, `decode` and `dump` on `RemoteProtocol<T>` are now plain members. External protocol
  classes must drop `override` on these methods, and listeners / dumpers that previously registered themselves from
  `setup()` must register from `to_code()` using the new `remote_base.add_listener()`,
  `remote_base.add_dumper()` and `remote_base.attach_receiver()` helpers. A protocol used only from C++ or a lambda
  (for example `id(tx).transmit<remote_base::NECProtocol>(data)`) needs `remote_base.request_protocol("<name>")` to
  keep its source in the build. [#19084](https://github.com/esphome/esphome/pull/19084)

### NFC: tags passed by reference, records in a fixed-size list

The `nfc` stack now avoids per-tag heap churn. Most lambdas keep compiling, but the shape of `tag` and
`get_records()` changed.

- **NFC**: `on_tag` and `on_tag_removed` triggers now receive `const nfc::NfcTag &` instead of a copy;
  `nfc::get_ha_tag_ndef()` / `nfc::has_ha_tag_ndef()` now take `const NfcTag &`. Range-for loops, `tag.get_uid()`,
  `tag.get_tag_type()`, `tag.has_ndef_message()` and `tag.get_ndef_message()` compile unchanged. Code that modified
  its local copy of the tag will now modify the shared reference.
  [#19902](https://github.com/esphome/esphome/pull/19902)
- **NFC**: `NdefMessage::get_records()` now returns `const nfc::NdefRecords &` (a `StaticVector` of `unique_ptr`)
  instead of `const std::vector<std::shared_ptr<NdefRecord>> &`. Iteration with `const auto &record : ...` and
  `record->...` still works. Copying an element out (`auto r = records[0];`) or copy-assigning one `NdefMessage`
  to another no longer compiles. [#19912](https://github.com/esphome/esphome/pull/19912)

### PN71xx (PN7150 / PN7160) shared base

- **PN71xx**: `pn7150` and `pn7160` now share a `pn71xx` base. `set_tag_emulation_message()` and
  `set_tag_write_message()` now take `(const std::string &, bool)` instead of `optional<>` values; lambdas passing a
  plain string are unaffected. The action and condition classes (`pn7150::EmulationOnAction` and friends) are
  removed in favour of `register_apply_action` / `register_apply_condition`. `TestMode` moved from the `pn7150` and
  `pn7160` namespaces to `pn71xx`, so lambdas calling `set_test_mode()` must now use `pn71xx::TestMode`.
  [#19589](https://github.com/esphome/esphome/pull/19589)

### Climate IR mode storage

- **Climate IR**: The protected `supports_cool_`, `supports_heat_`, `supports_heat_cool_`, `supports_dry_` and
  `supports_fan_only_` fields are replaced by one `climate::ClimateModeMask modes_`. External components that
  derived from `ClimateIR` and read or wrote the booleans must switch to the mask.
  [#19580](https://github.com/esphome/esphome/pull/19580)

  ```cpp
  // Before
  if (this->supports_heat_) { ... }
  this->supports_dry_ = true;
  // After
  if (this->modes_.count(climate::CLIMATE_MODE_HEAT)) { ... }
  this->set_mode_supported_(climate::CLIMATE_MODE_DRY, true);
  ```

### Audio files are flash constants

- **Audio File**: Codegen now emits each `audio_file` entry as a `constexpr audio::AudioFile` in flash and the id
  resolves to `const audio::AudioFile *`. `SpeakerMediaPlayer::play_file`, `AudioPipeline::start_file`,
  `AudioReader::start` and `NamedAudioFile::file` now take `const audio::AudioFile *`. Passing `id(my_file)` still
  works; only C++ that stored the id in a non-const `audio::AudioFile *` needs a `const` added.
  [#20072](https://github.com/esphome/esphome/pull/20072)

### Home Assistant action internals

- **API**: `HomeAssistantServiceCallAction`, the internal class codegen builds for `homeassistant.action`,
  `homeassistant.event` and `homeassistant.tag_scanned`, no longer has `set_service`, `init_data`,
  `init_data_template`, `init_variables`, `add_data`, `add_data_template` or `add_variable`, and its constructor
  changed; `TemplatableStringValue` and `TemplatableKeyValuePair` are removed. External components should use the
  documented `CustomAPIDevice` methods. A map with more than 255 entries is now rejected at config validation.
  [#20237](https://github.com/esphome/esphome/pull/20237)

  ```cpp
  // Before
  auto *a = new HomeAssistantServiceCallAction<>(global_api_server, false);
  a->set_service("light.turn_on");
  a->init_data(1);
  a->add_data("entity_id", "light.kitchen");
  a->play();
  // After
  this->call_homeassistant_service("light.turn_on", {{"entity_id", "light.kitchen"}});
  ```

### Hoermann HCP lamp control

- **Hoermann HCP**: `toggle_light()` and `cancel_light_toggle()` are removed; lambdas that drove the lamp through
  them should use `id(hcp).set_light(!id(hcp).is_light_heading_on())`.
  [#19765](https://github.com/esphome/esphome/pull/19765)
{/* UNDOCUMENTED_API_CHANGES_END */}

### Breaking changes for developers

{/* BREAKING_CHANGES_DEVELOPERS_START */}
- **Light**: `LightState` and the restore pipeline were rewritten so a light's state is now assembled by generated
  lambdas rather than a fixed `restore_mode` switch; subclasses that reached into those internals need updating.
  [#18997](https://github.com/esphome/esphome/pull/18997)
- **Light**: `LightState` shrunk by 12 bytes per light; internal field layout changed.
  [#19711](https://github.com/esphome/esphome/pull/19711)
- **Core**: `Action::stop_complex` and `Action::is_running` are no longer virtual; overrides must be removed.
  [#19662](https://github.com/esphome/esphome/pull/19662)
- **Core**: Controller updates are now dispatched through generated direct calls rather than virtual overrides.
  [#19588](https://github.com/esphome/esphome/pull/19588)
- **Core**: `select` options are now stored in a shared `ConstVector` kept in flash; direct access to the old option
  vector no longer compiles. [#20117](https://github.com/esphome/esphome/pull/20117)
- **Core**: Static FreeRTOS task TCBs now live in internal RAM; code that relied on the previous placement must
  adjust. [#19426](https://github.com/esphome/esphome/pull/19426)
- **HTTP Request**: `set_url()` and `set_method()` now take `const char *` instead of `std::string`.
  [#19215](https://github.com/esphome/esphome/pull/19215)
- **Modbus Controller**: Removed deprecated helper shims from the `modbus_controller` namespace; use the
  equivalents under `modbus::helpers`. [#19076](https://github.com/esphome/esphome/pull/19076)
- **Modbus**: Removed the deprecated `send()` entry point and the `disable_crc` validation stub.
  [#19079](https://github.com/esphome/esphome/pull/19079),
  [#19078](https://github.com/esphome/esphome/pull/19078)
- **Sensor**: Removed the deprecated public `raw_state` member; use `get_raw_state()`.
  [#19077](https://github.com/esphome/esphome/pull/19077)
- **Template**: Removed the deprecated `bypass_before_arming()` helper.
  [#19075](https://github.com/esphome/esphome/pull/19075)
- **Nextion**: Removed the deprecated `get_wave_chan_id()`.
  [#19080](https://github.com/esphome/esphome/pull/19080)
- **Remote Base**: `encode`, `decode` and `dump` on `RemoteProtocol<T>` are no longer virtual; protocol classes must
  drop `override`. Listener and dumper registration moves from C++ `setup()` to codegen via
  `remote_base.add_listener()` / `remote_base.add_dumper()`; a protocol used only from C++ or a lambda must call
  `remote_base.request_protocol()`. [#19084](https://github.com/esphome/esphome/pull/19084)
- **Network**: Removed the deprecated `IPAddress::str()` from the host build.
  [#19528](https://github.com/esphome/esphome/pull/19528)
- **PN532 / NFC**: Removed runtime heap allocation from the frame and tag paths; `NfcTag` is passed to triggers by
  reference and the internal listener list is now in static storage.
  [#19744](https://github.com/esphome/esphome/pull/19744),
  [#19902](https://github.com/esphome/esphome/pull/19902),
  [#19912](https://github.com/esphome/esphome/pull/19912)
- **nRF52**: Builds now fetch only the nRF Connect SDK projects they need; external components relying on the full
  checkout must declare the modules they require.
  [#19735](https://github.com/esphome/esphome/pull/19735)
