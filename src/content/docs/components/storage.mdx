The `storage` component is the shared base layer for all ESPHome storage drivers. It provides a common
interface, a runtime registry that tracks every configured storage device (and notifies subscribers on
hotplug register/unregister), an asynchronous transfer worker for non-blocking copy/move, and globally
available file-operation actions.

On its own, `storage` exposes no files or entities — a storage driver component (such as `sd_storage`,
`usb_storage`, `nfs_client`, or `binary_storage`) is always needed on top of it to actually access a
device. You do not need to add `storage:` to your configuration manually; it is automatically loaded by
any storage driver that depends on it, and all of its settings are optional.

> [!WARNING]
> The storage interface is **experimental**. Breaking changes may occur in future ESPHome releases as the
> component and its drivers evolve.

```yaml
# Example configuration entry (all values shown are the defaults)
storage:
  copy_chunk_size: 16384
  max_blocking_transfer_size: 0
  task_stack_size: 8192
  task_priority: 1
  max_pending: 4
```

## Configuration variables

- **id** (*Optional*, [ID](/guides/configuration-types#id)): Manually specify the ID for this component.
- **copy_chunk_size** (*Optional*, int): Buffer size, in bytes, used when copying a file from one storage
  device to another (e.g. SD card to USB, or USB to a network share). Must be a multiple of 512 and between
  4096 and 131072. Larger values can speed up copies slightly at the cost of more RAM held during the copy;
  the default is a good fit for SD/USB media. Defaults to `16384` (16 kB).
- **max_blocking_transfer_size** (*Optional*, int): Maximum size, in bytes, that the *blocking* whole-file
  copy/read/write helpers are allowed to process in one call. Larger transfers are rejected with the
  `TRANSFER_TOO_LARGE` error instead of freezing the device — use the asynchronous transfer path (below)
  for those. `0` means unlimited. Defaults to `0`.

The following are tuning knobs for the asynchronous transfer worker. They only take effect on nodes where
the worker is compiled in (see below); on all other nodes they are accepted and ignored.

- **task_stack_size** (*Optional*, int): Stack size, in bytes, for the background worker task on platforms
  that have one (currently ESP32). Needs headroom for FATFS long-filename handling and NFS/lwIP transfers.
  Must be between 4096 and 32768. Defaults to `8192`.
- **task_priority** (*Optional*, int): FreeRTOS priority for the background worker task. Should be above
  idle and below networking-related tasks. Must be between 1 and 23. Defaults to `1`.
- **max_pending** (*Optional*, int): Maximum number of async copy/move requests queued at once. Must be
  between 1 and 16. Defaults to `4`. Submitting while the queue is full is rejected immediately.
- **max_streams** (*Optional*, int): Maximum number of concurrently open chunked read/write streams.
  Defaults to `4`.

## Asynchronous transfers

Storage I/O is blocking by design, so a large file transfer done synchronously would make the node
unresponsive for its duration. The built-in transfer worker moves copy/move off the main loop's critical
path. There is nothing to configure or enable:

- The worker is compiled in **automatically** whenever a path-based (filesystem or network) storage driver
  is configured. Nodes that only use raw storage (small memory ICs like FRAM/EEPROM) never pay any flash or
  RAM for it. Its RAM (request pool, task stack) is allocated lazily on first use.
- Per transfer, the worker automatically picks the best execution strategy: a background FreeRTOS task
  when the platform supports it **and** both involved storages declare task-safe I/O (e.g. SD cards on the
  dedicated SDMMC controller), or otherwise a loop-sliced engine that processes one chunk per main-loop
  iteration (the only mode on platforms without a background task, and the fallback for bus-sharing
  drivers like SPI-attached SD cards). The API and behavior are identical either way — only timing differs.
- Completion callbacks always run on the main loop, regardless of which engine performed the transfer.
- Hotplug-safe: removing/unmounting a storage cancels its pending transfers and drains in-flight work
  before the device is torn down.

## File-operation actions

The following actions are available in automations on **every** node that has any storage driver — no
preparation in other components is needed. Paths are full VFS paths (mount point + file path, e.g.
`/sdcard/logs/temp.log`); the storage component routes them to the correct device automatically, so
multi-device setups work transparently.

These actions use the blocking helpers and are intended for *small* files (log lines, setpoints,
configuration values); `max_blocking_transfer_size` guards against misuse with large files.

### `storage.file_write` / `storage.file_append` Action

Writes content to a file. `file_write` truncates the file first, `file_append` appends and adds a trailing
newline by default (`newline: false` to disable; also available on `file_write`, default off there).

```yaml
on_value:
  - storage.file_append:
      path: /sdcard/logs/temp.log        # templatable
      format: "temp=%.1f at %s"          # printf-style, like logger.log
      args: [x, 'id(sntp_time).now().strftime("%H:%M")']
  - storage.file_write:
      path: /sdcard/state/last.txt
      content: !lambda 'return to_string(x);'   # alternative to format/args
```

- **path** (**Required**, string, [templatable](/automations/templates)): Full VFS path of the file.
- **content** (*Optional*, string, [templatable](/automations/templates)): The content to write. Exactly
  one of `content` or `format` must be given.
- **format** (*Optional*, string): printf-style format string, rendered with **args** — same syntax as
  [`logger.log`](/components/logger#logger-log-action).
- **args** (*Optional*, list of [lambda](/automations/templates#lambda)): Arguments for `format`.
- **newline** (*Optional*, boolean): Append a trailing newline. Defaults to `true` for `file_append`,
  `false` for `file_write`.

Errors (no device mounted for the path, write failure) are logged as warnings; the automation continues.

### `storage.file_read` Action

Reads a file, optionally extracts a value from its content through a chainable pipeline, and delivers the
result to a [global variable](/components/globals) and/or an `on_value` trigger.

```yaml
- storage.file_read:
    path: /sdcard/config/device.conf
    extract:                 # steps run in order, each on the previous result
      - key: setpoint        # take the value of a "setpoint=..." line
        separator: "="       #   (separator defaults to "=")
      - trim: true           # strip surrounding whitespace
    to_global: my_setpoint   # converted automatically to the global's type
    on_value:                # x = extracted value (std::string)
      - logger.log:
          format: "setpoint is now %s"
          args: ["x.c_str()"]
```

- **path** (**Required**, string, [templatable](/automations/templates)): Full VFS path of the file.
- **extract** (*Optional*, list): Extraction pipeline. Each step is exactly one of:
  - **line** (int): Pick the Nth line (1-based).
  - **split** (string) + **index** (*Optional*, int): Split at a separator string and pick the Nth element
    (0-based, defaults to `0`).
  - **key** (string) + **separator** (*Optional*, string, default `=`): Find the first line starting with
    `<key><separator>` and yield the remainder.
  - **regex** (string) + **group** (*Optional*, int): Match a regular expression (ECMAScript grammar) and
    yield the given capture group. Defaults to group 1 when the pattern has capture groups, otherwise the
    whole match. The pattern is validated at config time. Note: regex support compiles in `std::regex`
    (roughly 50–100 kB of flash) — it only does so when a configuration actually uses a `regex:` step.
  - **trim** (boolean): Strip leading/trailing whitespace.
- **to_global** (*Optional*, [ID](/guides/configuration-types#id)): A global variable to assign the result
  to. `float`, `int`, `bool` and `std::string` globals are supported; the string result is converted
  automatically. If conversion fails, the global is left unchanged and a warning is logged.
- **on_value** (*Optional*, [Automation](/automations/basics)): Triggered with the extracted value as
  `x` (an `std::string`).

At least one of `to_global` or `on_value` is required. If the file is missing or an extraction step fails
(line out of range, key not found, regex not matching), a warning is logged, the global stays untouched and
`on_value` does not fire.

Extraction of values from JSON files (JSON-pointer based) is planned as a follow-up.

## Behavior notes

The synchronous helpers keep individual blocking calls short (chunked I/O with watchdog feeding), but very
large synchronous transfers can still make the device temporarily unresponsive — cap them with
`max_blocking_transfer_size` and let the asynchronous worker handle anything bigger.
