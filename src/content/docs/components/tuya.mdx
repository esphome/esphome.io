The `tuya` component creates a serial connection to the Tuya MCU for platforms to use.

<Image src="/images/tuya.png" width={300} height={158} layout="constrained" alt="" />

The `tuya` serial component requires a [UART bus](/components/uart) to be configured.
Put the `tuya` component in the config and it will list the possible devices for you in the config log.

```yaml
# Register the Tuya MCU connection
tuya:
```

## Configuration variables

- **time_id** (*Optional*, [ID](/guides/configuration-types/#id)): Some Tuya devices support obtaining local time from ESPHome.
  Specify the ID of the [Time](/components/time/) which will be used.

- **force_time_sync** (*Optional*, boolean): Send the local time to the MCU once a minute, on top of the replies to
  its own time requests and the resend after each time source sync. Use it for MCUs whose display clock drifts
  between updates. Requires `time_id`. Defaults to `false`.
  A Tuya MCU asks for time in one of two ways: a local time request (command `0x1C`, time zone applied) or a GMT
  request (command `0x0C`). This option only sends local time, so it has no effect on an MCU that asks for GMT. With
  the logger at `DEBUG`, the line "Sending local time" or "Sending gmt time" shows which one your MCU uses.

- **status_pin** (*Optional*, [Pin Schema](/guides/configuration-types/#pin-schema)): Some Tuya devices support WiFi status reporting ONLY
  through gpio pin.
  Specify the pin reported in the config dump or leave empty otherwise.
  More about this on the [Tuya Developer Documentation](https://developer.tuya.com/docs/iot/tuya-cloud-universal-serial-port-access-protocol?id=K9hhi0xxtn9cb#title-7-Query%20working%20mode).

- **ignore_mcu_update_on_datapoints** (*Optional*, list): A list of datapoints to ignore MCU updates for. Useful for
  certain broken/erratic hardware and debugging.

- **heartbeat** (*Optional*, boolean): Set to `false` for an MCU that does not answer the heartbeat. The
  initialization then starts at the product query and the working mode is not queried. An `mcu_watchdog` with an
  action other than `disable` cannot be used. See [MCU Without Heartbeat](#mcu-without-heartbeat). Defaults to
  `true`.

- **datapoint_ack** (*Optional*, boolean): Answers each datapoint of a report of the MCU with an acknowledgement. Some
  MCUs repeat a report until they get one. Defaults to `false`.

- **mcu_watchdog** (*Optional*, mapping): Acts when the MCU stops answering heartbeats, which ends a stall of the
  serial transmitter of the MCU. Off when not configured. See [MCU Watchdog](#mcu-watchdog).

  - **action** (*Optional*, string): What is done after `missed_heartbeats` unanswered heartbeats. Defaults to
    `reboot`.

    - `reboot`: Reboots the module, as the original Tuya module firmware does.
    - `reset`: Holds the TX pin of the UART bus low for `reset_time`, without a reboot of the module.
    - `disable`: Turns the watchdog off, for a configuration that gets the block from a package.

  - **missed_heartbeats** (*Optional*, int): The number of unanswered heartbeats that starts the action.
    Range `1` to `20`. Defaults to `6`, the value of the original Tuya module firmware (TuyaOS 3.11): six 15 second
    heartbeats.
    Not accepted with `action: disable`.

  - **reset_time** (*Optional*, [Time](/guides/configuration-types/#time)): How long the TX pin is held low.
    Range `50ms` to `5s`. Defaults to `500ms`. Only accepted with `action: reset`.

Automations:

- **on_datapoint_update** (*Optional*): An automation to perform when a Tuya datapoint update is received. See [`on_datapoint_update`](#tuya-on_datapoint_update).

## Tuya Automation

<span id="tuya-on_datapoint_update"></span>

### `on_datapoint_update`

This automation will be triggered when a Tuya datapoint update is received.
A variable `x` is passed to the automation for use in lambdas.
The type of `x` variable is depending on `datapoint_type` configuration variable:

- *raw*: `x` is `std::vector<uint8_t>`
- *string*: `x` is `std::string`
- *bool*: `x` is `bool`
- *int*: `x` is `int`
- *uint*: `x` is `uint32_t`
- *enum*: `x` is `uint8_t`
- *bitmask*: `x` is `uint32_t`
- *any*: `x` is <APIStruct text="tuya::TuyaDatapoint" path="tuya::TuyaDatapoint" />

```yaml
tuya:
  on_datapoint_update:
    - sensor_datapoint: 6
      datapoint_type: raw
      then:
        - lambda: |-
            ESP_LOGD("main", "on_datapoint_update %s", format_hex_pretty(x).c_str());
            id(voltage).publish_state((x[0] << 8 | x[1]) * 0.1);
            id(current).publish_state((x[3] << 8 | x[4]) * 0.001);
            id(power).publish_state((x[6] << 8 | x[7]) * 0.1);
    - sensor_datapoint: 7 # sample dp
      datapoint_type: string
      then:
        - lambda: |-
            ESP_LOGD("main", "on_datapoint_update %s", x.c_str());
    - sensor_datapoint: 8 # sample dp
      datapoint_type: bool
      then:
        - lambda: |-
            ESP_LOGD("main", "on_datapoint_update %s", ONOFF(x));
    - sensor_datapoint: 6
      datapoint_type: any # this is optional
      then:
        - lambda: |-
            if (x.type == tuya::TuyaDatapointType::RAW) {
              ESP_LOGD("main", "on_datapoint_update %s", format_hex_pretty(x.value_raw).c_str());
            } else {
              ESP_LOGD("main", "on_datapoint_update %hhu", x.type);
            }
```

### Configuration variables

- **sensor_datapoint** (**Required**, int): The datapoint id number of the sensor.
- **datapoint_type** (*Optional*, string): The datapoint type one of *raw*, *string*, *bool*, *int*, *uint*, *enum*,
  *bitmask* or *any*.
- See [Automation](/automations).

## MCU Watchdog

The serial transmitter of some Tuya MCUs can stall while the rest of the MCU keeps running. This has been observed on
BHT-8000 series thermostats. The display and the buttons of the device still work, but the last bytes of a frame stay
unsent until the MCU transmits again, so every reply and every report reaches the module late. In ESPHome the entities
stop following the device, commands seem to be ignored and heartbeat replies arrive seconds late. The MCU does not leave
this state by itself.

The component counts heartbeats that the MCU does not answer. A heartbeat is unanswered when no reply arrives within
1 second and none within 1 second after it was sent once more. A reply that arrives later does not count. Two
heartbeats in a row that are answered at the first send take one off the count again. A reply to the second send takes
nothing off, because a stalled MCU answers late. An MCU that skips a heartbeat now and then is therefore never acted
on, a silent one after `missed_heartbeats` heartbeats in a row, and one that answers only some of its heartbeats in
time after some more. The action runs when the count reaches `missed_heartbeats`.

### Reboot

With `mcu_watchdog` configured the module reboots after `missed_heartbeats` unanswered heartbeats, 6 by default, which
are sent 15 seconds apart, as the original Tuya module firmware does. Without it the module never reboots for this
reason. The MCU is not reset and keeps its settings. As in the original firmware, the module does not reboot before
the MCU has answered the working mode query, so an MCU that never answers does not cause a reboot loop. Heartbeats
left unanswered before that reply do not count towards the reboot. This action is available on all platforms.

```yaml
tuya:
  mcu_watchdog:
    action: reboot
    missed_heartbeats: 6
```

The reboot is logged before it happens:

```text
[E][tuya]: MCU left 6 heartbeats unanswered, rebooting
```

Before the working mode reply the count is logged instead, once until the MCU answers a heartbeat, and the
configuration dump says that the watchdog is not armed yet:

```text
[W][tuya]: MCU left 6 heartbeats unanswered before the working mode reply, not rebooting
[C][tuya]:   MCU Watchdog is not armed before the working mode reply of the MCU
```

### Reset

`action: reset` holds the TX pin of the UART bus low for `reset_time` and then releases it. On the BHT-002 thermostat
MCU this ends the stall, and the module keeps running: WiFi and the API connection stay up. The MCU keeps running and
keeps its settings. The pin is the `tx_pin` of the [UART bus](/components/uart/), there is no pin option of its own.

```yaml
tuya:
  mcu_watchdog:
    action: reset
    missed_heartbeats: 6
    reset_time: 500ms
```

- It needs a UART bus of the microcontroller itself with an `rx_pin` and a `tx_pin` that is not inverted, on ESP32,
  ESP8266, RP2040, BK72xx, RTL87xx or LN882x. Other buses are rejected when the configuration is validated.
  On RTL8710B the bus must be on the pins of a hardware UART and its pins must not set `open_drain`, `pullup` or
  `pulldown`. No other component may use the bus, and on ESP8266, BK72xx, RTL87xx and LN882x the logger must not
  write to its UART.
- It has been tested on BK72xx with the BHT-002 thermostat MCU. Whether a low TX line ends a stall of another MCU
  is not known; `reboot` is the action of the original firmware.
- Unlike `reboot` it also runs before the MCU has answered the working mode query.
- While the pin is held low nothing is sent and nothing is read. Afterwards the datapoints are queried again.
- The component shows a warning status until the MCU answers a heartbeat at the first send again. A late reply or a
  reply to the second send does not end it. When the MCU still leaves `missed_heartbeats` heartbeats unanswered after
  a reset, the pin is held low again.
- After three resets in a row that were skipped or brought no answer the module reboots, under the rule of
  `reboot`: not before the MCU has answered the working mode query. Until then the resets go on.
- The module also reboots, under the same rule, when the UART bus refuses to hold the pin low at run time, and it
  always reboots when the bus does not release the pin.
- A reset is skipped when the bus has not finished sending. The next `missed_heartbeats` unanswered heartbeats try
  again. A skipped reset counts as a reset that brought no answer.

The log shows the reset and its result. The configuration dump counts the resets since boot as `MCU Resets`, which
is the number of times the pin was held low:

```text
[W][tuya]: MCU left 6 heartbeats unanswered, holding TX low
[I][tuya]: MCU answers heartbeats again after the reset
[E][tuya]: MCU left 6 heartbeats unanswered after a reset, holding TX low again
[W][tuya]: UART bus did not finish sending, MCU reset skipped
[E][tuya]: MCU did not answer after 3 reset attempts in a row, rebooting
[E][tuya]: UART bus cannot hold TX low, rebooting
[E][tuya]: UART bus did not release TX after the MCU reset, rebooting
```

### Disable

```yaml
tuya:
  mcu_watchdog:
    action: disable
```

With the watchdog off an unanswered heartbeat is logged as a warning, once until the MCU answers again.

## MCU Without Heartbeat

Some devices have a module firmware that sends no heartbeat, and their MCU does not answer one. With the default
settings the log shows `Initialization failed at init_state 0` and the datapoints are never read.

```yaml
tuya:
  heartbeat: false
  datapoint_ack: true
```

With `heartbeat: false`:

- No heartbeat is sent. The product query is sent at start and repeated every 3 seconds until the MCU answers it.
- The working mode is not queried. The WiFi status is sent over the UART unless `status_pin` is set.
- The datapoints are queried after the first WiFi status reply of the MCU, or right after the product reply when
  `status_pin` is set. A step without a reply is tried again every 3 seconds. A WiFi status without a reply after
  three retries is logged as `Initialization failed at init_state 3`.
- A restart of the MCU is not detected. An `mcu_watchdog` block other than `action: disable` is rejected.

With `datapoint_ack: true` each datapoint of a `0x07` report is answered with command `0x07`, the datapoint id and
`0x00`, as the module firmware of these devices does. Without it such an MCU sends each report three times.

A known device is the [EZAIOT / XYZOO thermostat](https://devices.esphome.io/devices/EZAIOT-XYZOO-Thermostat) with
product id `dq6nlukkifyawj9n`, which uses 38400 baud. Its original module firmware (TuyaOS 3.3.31) sends no heartbeat
and answers every datapoint report.

## Serial Timing

The component follows the serial timing of the original Tuya module firmware:

- A heartbeat is sent every 3 seconds until the MCU has answered the working mode query, then every 15 seconds. After a
  restart of the MCU the interval is 3 seconds again.
- A command that needs a reply is sent once more if the MCU has not answered within 1 second. After the second second
  without a reply it is dropped. This includes datapoint writes: an MCU that does not report a written datapoint
  back receives the write twice, the next command waits 2 seconds and the log shows
  `Datapoint command got no report from the MCU, dropped`. A report of either kind (`0x07` or `0x22`) that holds
  the written datapoint is the reply to a datapoint write.
- A datapoint write that still waits behind another command is replaced by a newer write of the same datapoint, so
  a slow MCU gets the last value. Raw and string values are all sent. With 32 commands waiting a further datapoint
  write is dropped and the log shows `Datapoint ... command dropped`.
- Heartbeats and the acknowledgements of `datapoint_ack` go out ahead of the commands that wait.
- An incomplete frame of the MCU is dropped after 400 ms without a new byte.
- An initialization that failed starts again with the next heartbeat reply of the MCU, and the WiFi status is sent
  again in it. With `heartbeat: false` the open step is tried again every 3 seconds.
- An extended services frame (`0x34`) without a sub-command is ignored.
