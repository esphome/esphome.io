The `genibus_ble` component is a transport for the [GENIbus](/components/genibus/) bus. It sends GENIbus requests to
a Grundfos pump over Bluetooth Low Energy, the same way the Grundfos GO app does. It does not create any entities
itself. Device components on the bus use it to read the pump.

This component runs on the ESP32 only. It needs a [BLE Client](/components/ble_client/) with the MAC address of the
pump, which handles the Bluetooth connection. The BLE Client in turn needs the
[ESP32 BLE Tracker](/components/esp32_ble_tracker/).

```yaml
# Example configuration entry
genibus_ble:
```

## Configuration variables

- **ble_client_id** (*Optional*, [ID](/guides/configuration-types/#id)): The ID of the
  [BLE Client](/components/ble_client/) that connects to the pump. Required if you have more than one BLE Client.

- **master_address** (*Optional*, int): The GENIbus address that ESPHome uses for itself on the bus. Defaults to
  `0xF8`, the address that the Grundfos GO app uses.

- **id** (*Optional*, [ID](/guides/configuration-types/#id)): Manually specify the ID used for code generation.
  Required if you have more than one `genibus_ble` entry and a device component needs to pick one.

You can add more than one `genibus_ble` entry, one for each pump. Each entry needs its own BLE Client.

The response timeout of this transport is 1 second, and the quiet period after a timeout is 250 milliseconds. See
[How the Bus Works](/components/genibus/#how-the-bus-works). You cannot change these values.

Frames longer than 20 bytes are written in pieces of 20 bytes, and answers that arrive in several notifications are
put back together before they are checked.

## Connection and Pairing

The pump only answers on an encrypted link. When the BLE Client connects, this component starts pairing. The
connection counts as up 500 milliseconds after ESPHome has subscribed to the GENIbus notifications of the pump.
The pump can drop a request that arrives right after the subscription, so the component waits before the first
request. Until then, the bus sends no requests. You cannot change this wait.

If the pump does not offer the GENIbus characteristic, or ESPHome cannot subscribe to it, the component logs a
warning and disconnects. This frees the pump's connection for other devices. The BLE Client connects again later if
`auto_connect` is on.

> [!NOTE]
> The pump allows only one Bluetooth connection at a time. While ESPHome is connected, the Grundfos GO app cannot
> connect to the pump. To use the app, turn off the ESP32 or disconnect the BLE Client first.

## Troubleshooting

### Pairing Failed

If pairing fails, the log shows the warning `Pairing failed` and the component sets a warning status.

1. Allow pairing on the pump. How to do this depends on the pump model; see the manual of your pump. On a Grundfos
   ALPHA3, tap the Connect button briefly. The pump then starts the pairing itself, and no PIN is needed.
1. Let the BLE Client connect again, for example by restarting the ESP32.

The pump keeps the pairing through a loss of power, so you only need to pair once. It can keep more than one pairing,
for example with an ESP32 and a computer.

> [!WARNING]
> Do not hold buttons on the pump down while you try to pair. On a Grundfos ALPHA3, holding the Connect button for
> 2 seconds changes the control mode of the pump. If this happens, check the control mode and set it back.

### The Pump Is Not Found

- The pump allows only one Bluetooth connection. While a phone with the Grundfos GO app or another ESP32 is connected,
  the pump does not advertise and ESPHome cannot connect.
- A pump without power cannot be found either. If a heating controller switches the pump off, the connection comes
  back on its own when the pump has power again. This is not an error.

### No GENI Characteristic

If the log shows `No GENI characteristic, disconnecting`, the device at this MAC address does not offer the GENIbus
service. Check that the MAC address of the BLE Client belongs to the pump.

### Reconnects Fail Until Reboot (ESP-IDF 5.5.6)

The first connection works, but after a disconnect every new connection fails with `auth fail` until the ESP32
restarts. This is a bonding bug in ESP-IDF 5.5.6, see
[esphome#21880](https://github.com/esphome/esphome/issues/21880). Until it is fixed, you can use ESP-IDF 5.5.5
instead:

```yaml
esp32:
  framework:
    type: esp-idf
    version: 5.5.5
```

Remove the `version` line again once a fixed ESP-IDF version is available.
