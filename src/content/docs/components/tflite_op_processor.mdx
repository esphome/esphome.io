The `tflite_op_processor` component is a **library component**: it is loaded automatically as a dependency of
the `tflite_micro_runtime` component and of the third-party components that consume it, and it needs no
configuration of its own. Its one option, `operators`, pins the kernel set for a build that does not derive it
from a model (see [Configuration Variables](#configuration-variables)).

The `tflm_operators.h` header holds one X-macro table describing every operator the `esp-tflite-micro`
library can register (`TFLM_OP_AVAILABLE`, `TFLM_OP_CONDITIONAL`, `TFLM_OP_UNAVAILABLE`). The entry is the
single source of truth for both sides of the pipeline:

- **At configuration time**, `model_reader.py` reads the operator codes from the model's `.tflite` flatbuffer,
  and `op_manifest.py` parses the same table, so a model whose operators cannot be registered is rejected before
  anything is compiled. The companion `.txt` report is not consulted for this: the model file is authoritative.
- **At run time**, `OpResolverManager::register_ops()` reads the model's operator code list and registers only
  the operators actually used, through the table, on a `MicroMutableOpResolver` sized by
  `TFLITE_MICRO_MAX_OPERATORS`, which `tflite_micro_runtime` emits as the number of distinct operator codes of
  the widest configured model.

The `TFLM_OP_CONDITIONAL` entries name the `Add*()` method they need. `register_ops()` checks for that method with
`if constexpr`, so a model that needs one of those operators is reported as unsupported on a pinned
`esp-tflite-micro` release that does not provide it, instead of failing to compile. The table is written against
`esp-tflite-micro` 1.4.1, the version this component pins.

## Example configuration entry

Nothing has to be configured: operators are registered automatically from the model, and `debug: true` prints
the operator table that was registered for it:

```yaml
tflite_micro_runtime:
  - id: digit_reader
    model_type: image
    model: "models/digit_recognizer.tflite"
    # Operators are registered automatically from the model;
    # debug: true prints the operator table that was registered.
    debug: true
```

## Configuration Variables

`tflite_micro_runtime` derives the operator list from each model's `.tflite` file and loads this component
automatically, so nothing has to be configured for the normal case.

The `operators` option pins the kernel set instead, for a build that does not go through `tflite_micro_runtime`:

```yaml
tflite_op_processor:
  operators:
    - SOFTMAX
    - REDUCE_MIN
```

Every name is validated against the operator table, and the list is emitted as the `TFLM_OP_ENABLED_*` flags of
a selective build; a name the pinned `esp-tflite-micro` cannot register is a configuration error. When
`tflite_micro_runtime` is configured as well, the two sets are combined, so this can add kernels but never
remove one.

The component can also be loaded with no options at all, which is mainly useful when another component declares
it in its `DEPENDENCIES` (the ESPHome component tests do this):

```yaml
tflite_op_processor:
```
