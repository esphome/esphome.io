The `modbus_monitor` component runs automations for the requests and responses that a [Modbus](/components/modbus/)
hub handles. On a hub with the `server` role, that is each request the hub receives and the reply to it, sent by
this hub or another device. On a hub with the `client` role, that is each request the hub sends and the reply to it.

```yaml
# Example configuration entry
modbus_monitor:
  - on_request:
      - lambda: |-
          ESP_LOGD("modbus_monitor", "Request to %u, function 0x%02X", address, request[0]);
    on_response:
      - lambda: |-
          if (response[0] & 0x80) {
            ESP_LOGW("modbus_monitor", "Exception 0x%02X from %u for function 0x%02X", response[1], address,
                     request[0]);
          }
```

## Configuration Variables

- **modbus_id** (*Optional*, [ID](/guides/configuration-types#id)): The Modbus hub to watch. Automatically assigned
  when a single hub is configured.

- **on_request** (*Optional*, [Automation](/automations)): Runs for each request. See below.

- **on_response** (*Optional*, [Automation](/automations)): Runs for each response. See below.

At least one of `on_request` and `on_response` is required. Several `modbus_monitor` entries can watch the same hub.

## Automation Variables

- `address` (`uint8_t`): The address the request was sent to. `0` is a broadcast.
- `request` (`std::span<const uint8_t>`): The request PDU: function code followed by data, without address and CRC.
- `response` (`std::span<const uint8_t>`, `on_response` only): The response PDU, in the same form. An exception
  response has bit 7 of the function code set (`response[0] & 0x80`).

The data is only valid while the automation runs, so `delay`, `wait_until` and other actions that wait are rejected
in it. Copy what you need first. Keep the automation short: it runs in the hub's loop.

### Server Hub

`on_request` runs for every frame the hub reads as a request, for any address and for broadcasts. For a request to
one of this hub's [Modbus Server](/components/modbus_server/) devices, it runs before the device answers.
`on_response` runs for each reply the hub has sent, after the reply is written to the UART, and for the reply of
another device to a request the hub has seen. A reply that is dropped does not run it.

> [!NOTE]
> The hub tells a request from a reply by the order and shape of the frames. If a device does not answer, the next
> request that has the shape of a reply is taken for one, whatever its address, for example a single write or mask
> write (function codes `0x05`, `0x06`, `0x16`). Broadcasts are always read as requests.
>
> A reply from another device is paired with the last request by address and function code only, so a late reply
> to an earlier request can arrive with a newer one. If that is a concern, compare the reply's length with what
> the request asked for, as the example under [Listening Only](#listening-only-sniffer) does.

### Client Hub

`on_request` runs each time the hub sends a request, broadcasts and retries included, after the request is written
to the UART and after the device's `on_sent`. A request that was queued but never sent does not run it.
`on_response` runs for each response that matches the request the hub is waiting for, exception responses included,
after the device has handled it. A request without a response does not run it.

## Listening Only (Sniffer)

A hub with the `server` role and no [Modbus Server](/components/modbus_server/) devices never transmits, so it can
sniff a bus that other devices use. It needs only an `rx_pin`. For register values, use the
[Modbus Monitor Sensor](/components/sensor/modbus_monitor/). For anything else, use an automation, for example to
log every exchange on the bus:

```yaml
uart:
  - id: bus
    rx_pin: GPIOXX
    baud_rate: 9600

modbus:
  - uart_id: bus
    role: server

modbus_monitor:
  - on_response:
      - lambda: |-
          char hex[format_hex_pretty_size(modbus::MAX_PDU_SIZE)];
          ESP_LOGI("sniffer", "%u request:  %s", address, format_hex_pretty_to(hex, request.data(), request.size()));
          ESP_LOGI("sniffer", "%u response: %s", address, format_hex_pretty_to(hex, response.data(), response.size()));
```

To decode register values, check that the reply carries the registers the request asked for, so that a late reply
to an earlier read is not taken for the newer one's. The [Modbus Monitor Sensor](/components/sensor/modbus_monitor/)
makes this check before it publishes. For example, to log each register read on the bus:

```yaml
modbus_monitor:
  - on_response:
      - lambda: |-
          // Register reads only. A client hub also passes exception replies, which have bit 7 set.
          if ((request[0] != 0x03 && request[0] != 0x04) || response[0] != request[0] || request.size() < 5)
            return;
          const uint16_t start = encode_uint16(request[1], request[2]);
          const uint16_t count = encode_uint16(request[3], request[4]);
          // Skip a reply of the wrong length: it answers some other request.
          if (response.size() != 2u + count * 2u || response[1] != count * 2u)
            return;
          for (uint16_t i = 0; i < count; i++) {
            const unsigned reg = start + i;
            const unsigned value = encode_uint16(response[2 + i * 2], response[3 + i * 2]);
            ESP_LOGI("sniffer", "%u register %u = %u", address, reg, value);
          }
```

On the same bus, the hub can also answer as a Modbus Server: give it a `tx_pin` and devices, and it still sees the
exchanges of the others. A `client` hub sees only its own exchanges. Each hub has its own UART, so one ESPHome device
can sniff one bus and be a client or server on another. Most ESP32 chips have at least two hardware UARTs free for
buses; an ESP8266 has only one. See [UART](/components/uart/#hardware-uarts).
