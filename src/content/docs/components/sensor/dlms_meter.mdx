This component connects to smart meters that use the `DLMS/COSEM` protocol in PUSH mode over UART.

## Prerequisites

* You need to use an M-Bus to UART adapter to connect the ESP board to the smart meter.
* If your meter uses encryption, you will need to obtain a decryption key from your energy provider.

## Configuration

```yaml
# UART configuration can be different depending on your meter and ESP board.
# You only need to configure the RX channel. TX is not used.
uart:
  id: uart_dlms_bus
  baud_rate: 2400
  rx_pin: GPIOXX
  rx_buffer_size: 2000

dlms_meter:
  id: dlms_meter_hub
  uart_id: uart_dlms_bus

sensor:
  - platform: dlms_meter
    dlms_meter_id: dlms_meter_hub
    obis_code: "1.0.1.7.0.255"
    name: "Active power taken from grid"
```

## Configuration Variables

- **id** (*Optional*, [ID](/guides/configuration-types/#id)): The ID of the `dlms_meter` component.
- **uart_id** (*Optional*, [ID](/guides/configuration-types/#id)): The ID of the UART component that is
connected to the smart meter.
- **receive_timeout** (*Optional*, [Time](/guides/configuration-types/#time)):
  The timeout for receiving a complete frame. Default: `1000ms`.
- **decryption_key** (*Optional*, string): Specify if your smart meter uses encryption. You should request this key
from your electricity provider (32 hex characters, case-insensitive). Example: `0123456789ABCDEF0123456789ABCDEF`
- **auth_key** (*Optional*, string): Authentication key. Specify if your smart meter uses encryption with
authentication. You should request this key from your electricity provider. Example: `0123456789ABCDEF0123456789ABCDEF`
- **skip_crc** (*Optional*, boolean): Skip CRC check. Some smart meters use the wrong polynomial to calculate CRC.
In such cases, you can use this flag as a workaround. Defaults to `false`.
- **custom_patterns** (*Optional*, list): Specifies custom parsing patterns. Use this for meters with a payload format
  not supported by default. The available patterns are described in the README of
  [esphome-libs/dlms_parser](https://github.com/esphome-libs/dlms_parser)

### Multiple Meters

You can connect several smart meters to the ESP board using separate UART buses for each meter.

```yaml
dlms_meter:
  - id: meter_1
    uart_id: uart_meter_1
  - id: meter_2
    uart_id: uart_meter_2

sensor:
  - platform: dlms_meter
    dlms_meter_id: meter_1
    obis_code: "1.0.1.7.0.255"
    name: "Meter 1 Active power"
  - platform: dlms_meter
    dlms_meter_id: meter_2
    obis_code: "1.0.1.7.0.255"
    name: "Meter 2 Active power"
```

## Platforms

### Sensor, Text Sensor, and Binary Sensor

All platforms (`sensor`, `text_sensor`, `binary_sensor`) support dynamic mapping using the `obis_code` property.
This allows you to decode nearly any property your meter emits.

- **dlms_meter_id** (*Optional*, [ID](/guides/configuration-types/#id)): Manually specify the ID of the
`dlms_meter` hub if you have [multiple meters](#multiple-meters).
- **obis_code** (**Required for dynamic mapping**, string): The OBIS code of the value you want to read.
  The code supports flexible formats like `1-0:32.7.0` or `1.0.32.7.0.255`.

When defining your sensors, it is recommended to include standard ESPHome sensor properties such as
`unit_of_measurement`, `accuracy_decimals`, `device_class`, and `state_class`.

Here is an example of how to configure an energy sensor so it displays correctly with Home Assistant's Energy Dashboard:

```yaml
sensor:
  - platform: dlms_meter
    obis_code: "1.0.1.8.0.255"
    name: "Energy Consumed"
    unit_of_measurement: "kWh"
    accuracy_decimals: 3
    device_class: energy
    state_class: total_increasing

text_sensor:
  - platform: dlms_meter
    obis_code: "0.0.1.0.0.255"
    name: "Timestamp"
```

### Finding Your Meter's OBIS Codes

Before using this method, check if your energy provider provides a list the OBIS codes sent by the smart meter.

Temporarily increase the logging level to see which OBIS codes your meter is sending.
For raw smart meter packet data, change both `level` and `dlms_meter` below to `VERY_VERBOSE`.

```yaml
logger:
  level: VERBOSE
  initial_level: DEBUG
  logs:
    dlms_meter: VERBOSE
```

### Migrating from Legacy Keys

The predefined sensor keys (for example `voltage_l1` or `timestamp`) and the `provider` option were removed in
2026.11.0. Replace each legacy key with an entry that sets `obis_code` to the code listed below, as shown in the
examples above. For sensors, the legacy keys also set the unit, accuracy, device class and state class shown in
the list, so add those to each new entry. Remove `provider` from the hub; for `provider: netznoe` you can use the
working configuration from [Netz NOE](#netz-noe) instead.

**Sensors:**

- **voltage_l1** (`1.0.32.7.0.255`; `V`, 1 decimal, `voltage`, `measurement`): Voltage Phase 1.
- **voltage_l2** (`1.0.52.7.0.255`; `V`, 1 decimal, `voltage`, `measurement`): Voltage Phase 2.
- **voltage_l3** (`1.0.72.7.0.255`; `V`, 1 decimal, `voltage`, `measurement`): Voltage Phase 3.
- **current_l1** (`1.0.31.7.0.255`; `A`, 2 decimals, `current`, `measurement`): Current Phase 1.
- **current_l2** (`1.0.51.7.0.255`; `A`, 2 decimals, `current`, `measurement`): Current Phase 2.
- **current_l3** (`1.0.71.7.0.255`; `A`, 2 decimals, `current`, `measurement`): Current Phase 3.
- **active_power_plus** (`1.0.1.7.0.255`; `W`, 0 decimals, `power`, `measurement`): Active power taken from grid.
- **active_power_minus** (`1.0.2.7.0.255`; `W`, 0 decimals, `power`, `measurement`): Active power put into grid.
- **active_energy_plus** (`1.0.1.8.0.255`; `Wh`, 0 decimals, `energy`, `total_increasing`): Cumulative active energy
 taken from grid.
- **active_energy_minus** (`1.0.2.8.0.255`; `Wh`, 0 decimals, `energy`, `total_increasing`): Cumulative active energy
 exported to grid.
- **reactive_energy_plus** (`1.0.3.8.0.255`; `Wh`, 0 decimals, `energy`, `total_increasing`): Reactive energy taken
 from grid.
- **reactive_energy_minus** (`1.0.4.8.0.255`; `Wh`, 0 decimals, `energy`, `total_increasing`): Reactive energy
 exported to grid.
- **power_factor** (`1.0.13.7.0.255`; no unit, 3 decimals, `power_factor`, `measurement`): Power factor.

**Text Sensors:**

- **timestamp** (`0.0.1.0.0.255`): Timestamp included in the received frame.
- **meternumber** (`0.0.96.1.0.255`): Meter number reported by the device.

### Landis+Gyr E450

```yaml
dlms_meter:
  # ...
  decryption_key: "YOUR_32_CHAR_HEX_KEY"
  custom_patterns:
    - pattern: "F, TDTM"
      name: "DateTime"
```

### Landis+Gyr ZMF100

This meter uses the wrong CRC polynomial, so you have to skip the CRC check.

```yaml
dlms_meter:
  # ...
  skip_crc: true
```

### Kamstrup Omnipower

This meter requires an encryption key and, in some cases, an authentication key.

```yaml
dlms_meter:
  # ...
  decryption_key: "YOUR_32_CHAR_HEX_KEY"
  auth_key: "YOUR_32_CHAR_AUTH_KEY" # Add if required by your provider
  custom_patterns:
    - pattern: "F, TSTR"
      name: "Obis List Ver"
```

### KAIFA MA309M

This meter requires the custom patterns below to decode the meter ID and timestamp correctly.

```yaml
dlms_meter:
  # ...
  decryption_key: "YOUR_32_CHAR_HEX_KEY"
  custom_patterns:
    - pattern: "L, TSTR"
      name: "MeterID"
      default_obis: "0.0.96.1.0.255"
    - pattern: "F, TDTM"
      name: "DateTime"
      default_obis: "0.0.1.0.0.255"
```

## Host Platform

On the [host platform](/components/host/), the component needs the Mbed TLS development files,
even when no `decryption_key` is set.

On Debian, Ubuntu and Raspberry Pi OS:

```sh
apt install libmbedtls-dev
```

On macOS with Homebrew:

```sh
brew install mbedtls
```
