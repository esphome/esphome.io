The `modbus_monitor` sensor platform publishes a register value from the Modbus traffic a
[Modbus](/components/modbus/) hub sees, without sending anything itself. It needs no lambda: give it the device
address, the register and the value type.

On a hub with the `server` role and no [Modbus Server](/components/modbus_server/) devices, the hub only listens, as a
sniffer, so the sensors read the exchanges of other devices on the bus, for example an inverter polling a battery or
a meter. On a hub with the `client` role, they read the responses to the requests this hub sends.

```yaml
# Example configuration entry: listen to a bus without transmitting
uart:
  - id: bus
    rx_pin: GPIOXX
    baud_rate: 9600

modbus:
  - uart_id: bus
    role: server

sensor:
  - platform: modbus_monitor
    address: 1
    register: 100
    name: "Register 100"
  - platform: modbus_monitor
    address: 1
    register: 101
    value_type: S_WORD
    name: "Register 101"
  - platform: modbus_monitor
    address: 1
    register: 102
    value_type: FP32
    name: "Registers 102-103"
```

## Configuration Variables

- **address** (**Required**, int): The address of the device the register belongs to.

- **register** (**Required**, int): The register, as the address in the request on the wire. This is the same
  number the `address` of a [Modbus Controller Sensor](/components/sensor/modbus_controller/) takes. A register
  number matches holding and input reads alike; on a device whose tables differ, the sensor publishes both.

- **value_type** (*Optional*): How the register data is decoded. Defaults to `U_WORD`. Takes the same value types
  as the [Modbus Controller Sensor](/components/sensor/modbus_controller/), with the same meaning. A value wider
  than one register, for example `U_DWORD` or `FP32`, starts at `register` and takes the registers after it.

- **modbus_id** (*Optional*, [ID](/guides/configuration-types#id)): The Modbus hub to watch. Automatically assigned
  when a single hub is configured.

- All other options from [Sensor](/components/sensor).

## When a Value Is Published

The sensor publishes each time the hub sees an exchange with its device that covers all of the value's registers:

- **Reads** of holding or input registers (function codes `0x03`, `0x04` and `0x17`): the value is taken from the
  response. Any read covering the registers counts, whatever its start address and length, as long as the response
  carries exactly the registers requested. For `0x17` that is the read half only: the registers it writes are not
  published. An exception response publishes nothing.
- **Writes** of registers (function codes `0x06` and `0x10`), once the device confirms them: for `0x06` the response
  repeats the request, for `0x10` it repeats the start address and count. The value is taken from the request. A
  write without a confirmation publishes nothing, unless the next frame repeats a `0x06` write byte for byte: a
  `server` hub takes that for the echo.

Coils and discrete inputs are not supported.

A device that is polled often publishes often. To limit that, use [sensor filters](/components/sensor#sensor-filters)
such as `throttle` or `delta`.

> [!NOTE]
> On a `server` hub, a request without a response can be paired with the frame that follows it. See
> [Modbus Monitor](/components/modbus_monitor/#server-hub). A late reply to an earlier read is not published when
> its length differs from what the newer request asked for, but one of the same length cannot be told apart and is
> published under the newer request's registers.

For anything the sensor does not cover, a [Modbus Monitor](/components/modbus_monitor/) automation gets the raw
request and response.
