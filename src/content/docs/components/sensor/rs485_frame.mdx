The `rs485_frame` sensor platform exposes hub-state diagnostics (frame counters,
CRC failures, queue depth, etc.) as Home Assistant sensors. It requires the
[RS485 Frame](/components/rs485_frame/) hub to be configured.

User payload decoding is **not** done on this platform. To decode the contents
of received frames, use [`on_frame:` on the hub](/components/rs485_frame/#configuration-variables)
with `platform: template` sensors — that pattern handles every case from a
single bit-field LED mask through a multi-field temperature/text frame.

## Configuration variables

- **rs485_frame_id** (**Required**, [ID](/guides/configuration-types#id)): The ID of the `rs485_frame` hub.
- **decode** (**Required**, string): Which hub diagnostic value to publish. Each
  decode value carries Home-Assistant-conformant defaults (state class, unit, and
  for `last_keepalive_ms` a device class) so you do not have to set them yourself:

  | decode | Description | `state_class` | `unit_of_measurement` | other |
  |---|---|---|---|---|
  | `frames_received` | Validated frames received. | `total_increasing` | `frames` | |
  | `crc_failures` | Frames that failed validation (CRC or structural). | `total_increasing` | `frames` | |
  | `discarded_frames` | Frames abandoned mid-receive (buffer overflow or intra-frame timeout), before CRC/structural validation ever ran. | `total_increasing` | `frames` | |
  | `commands_sent` | User commands transmitted (idle keepalives excluded). | `total_increasing` | `commands` | |
  | `command_drops` | Commands dropped (queue full or sniffer mode). | `total_increasing` | `commands` | |
  | `last_keepalive_ms` | Gate-frame interval in ms. | `measurement` | `ms` | `device_class: duration` |
  | `queue_depth` | Current TX queue depth (including any pending delayed). | `measurement` | `commands` | |
  | `response_success` | [`response_monitor`](/components/rs485_frame/#response-monitor) entry: confirmed presses. | `total_increasing` | `occurrences` | requires `monitor_id` |
  | `response_fail` | `response_monitor` entry: addressed field arrived with the wrong content. | `total_increasing` | `occurrences` | requires `monitor_id` |
  | `response_timeout` | `response_monitor` entry: window elapsed with nothing addressed arriving at all. | `total_increasing` | `occurrences` | requires `monitor_id` |
  | `response_not_applicable` | `response_monitor` entry: a `changed_gated` occurrence whose gate did not hold at trigger time. | `total_increasing` | `occurrences` | requires `monitor_id` |
  | `response_orphan` | `response_monitor` entry: signature matched with no trigger pending. | `total_increasing` | `occurrences` | requires `monitor_id` |

- **monitor_id** (**Required** with a `response_*` decode, string): The `name:` of the
  [`response_monitor`](/components/rs485_frame/#response-monitor) entry this sensor reads
  from. Not valid with any other `decode:` value.
- **update_interval** (*Optional*, [Time](/guides/configuration-types#time)): How often to
  check the underlying counter. Defaults to `60s` for `frames_received` and
  `last_keepalive_ms` (which change on nearly every RX frame on a live bus) and `1s` for
  every other `decode:` (which only changes on rare error/edge conditions, so a real
  occurrence still surfaces promptly).

All other options from [Sensor](/components/sensor/#base-sensor-configuration).
Every diagnostic also defaults to `entity_category: diagnostic`. You can override
any of the per-decode defaults by setting the same key explicitly in YAML.

Sensors publish on change only: even though `update_interval` gates how often the
underlying counter is checked, a value that has not advanced since the last check does
not generate API traffic, so no `throttle` filter is required for steady-state operation.
During bring-up, lower `update_interval` to watch a counter move sooner; for per-frame detail, use
the hub's [`dump_frames:`](/components/rs485_frame/#configuration-variables) or
[`sniffer_stats:`](/components/rs485_frame/#optional-enable-sniffer-stats) instead.

## Example

```yaml
sensor:
  - platform: rs485_frame
    rs485_frame_id: pool
    name: "Frames Received"
    decode: frames_received

  - platform: rs485_frame
    rs485_frame_id: pool
    name: "CRC Failures"
    decode: crc_failures

  - platform: rs485_frame
    rs485_frame_id: pool
    name: "Queue Depth"
    decode: queue_depth

  - platform: rs485_frame
    rs485_frame_id: pool
    name: "Lights Confirm Success"
    decode: response_success
    monitor_id: lights_confirm

  - platform: rs485_frame
    rs485_frame_id: pool
    name: "Lights Confirm Fail"
    decode: response_fail
    monitor_id: lights_confirm
```

## Interpreting the counters

- A rising `crc_failures` with zero `frames_received` usually means the wrong
  baud rate or UART settings.
- A small steady `crc_failures` alongside healthy `frames_received` suggests
  `crc.type` or `crc.rx_accept` needs adjustment.
- `discarded_frames` counts frames that never reached CRC/structural validation at all — a
  frame that overflowed `max_frame_length` or sat mid-receive past the intra-frame timeout. A
  rising count usually points to bus noise, a wrong baud rate, or a `max_frame_length` set too
  small for the bus.
- `command_drops` should stay at 0 in normal operation. With `queue_policy: replace_latest`,
  every press that arrives while another command is pending increments the counter — useful for
  detecting button mash. With `queue_policy: fifo`, drops indicate the queue is too small.
- `last_keepalive_ms` shows the bus poll interval. Sudden changes here often
  indicate bus contention or controller reboots.
- A rising `response_fail` alongside a healthy `response_success` rate on the same entry
  usually means the wrong response carrier or field was picked — double-check the
  `response_fields:` addressing against a real capture.
- A rising `response_timeout` with zero `response_success`/`response_fail` on an otherwise
  healthy bus usually means `window:` is too short for that response, or the trigger's
  `button_id:`/`frame_type:` never actually matches a transmitted frame.
- `response_orphan` counts a confirmed signature with no trigger pending — commonly someone
  operating the physical panel directly, not a bug in the monitor.
