OpenTherm (OT) is a standard communications protocol used in central heating systems for the communication between
central heating appliances and a thermostatic controller. As a standard, OpenTherm is independent of any single
manufacturer. A controller from manufacturer A can in principle be used to control a boiler from manufacturer B.

The `opentherm42` component implements version 4.2 of the OpenTherm protocol, covering the data classes of the
specification as completely as possible: boiler status and control, configuration, remote commands, sensor data,
remote boiler parameters, transparent slave parameters, fault history and special applications (ventilation,
solar storage, cooling, remote override).

The older [OpenTherm](/components/opentherm/) component is smaller and covers fewer data points. `opentherm42` has
more entities, checks the answers of the boiler, tolerates transient errors and reports the health of the
communication. See the [OpenTherm](/components/opentherm/) documentation for background on the protocol.

> [!NOTE]
> This component acts only as an OpenTherm master (for example, a thermostat or controller) and not as a slave or
> gateway. Your existing thermostat is not usable while you use ESPHome with this component to control your boiler.

> [!NOTE]
> The component needs an ESP32 or ESP8266. See [Data Link](#data-link) for the details.

Most adapters label the `in` and `out` pins relative to themselves; this component labels them relative to the

## Quick Glossary

- CH: Central Heating
- DHW: Domestic Hot Water
- HC1, HC2: Heating circuits 1 and 2
- TSP: Transparent Slave Parameter, a manufacturer-specific boiler parameter

## Minimal Example

This reads a few values from the boiler and lets Home Assistant set the central heating temperature. The control
setpoint is the only required entity. Without the `ch_enable` switch the boiler is never asked to heat.

```yaml
opentherm42:
  in_pin: GPIOXX
  out_pin: GPIOXX

switch:
  - platform: opentherm42
    control_and_status_information_master_status_ch_enable:
      name: "CH Enable"
      restore_mode: RESTORE_DEFAULT_ON

number:
  - platform: opentherm42
    control_and_status_information_control_setpoint:
      name: "Control Setpoint"
      initial_value: 40

binary_sensor:
  - platform: opentherm42
    control_and_status_information_boiler_status_flame_status:
      name: "Flame"

sensor:
  - platform: opentherm42
    sensor_and_informational_data_boiler_water_temperature:
      name: "Boiler Water Temperature"
```

## How Updates Work

OpenTherm is a slow protocol: a master asks the boiler for one value at a time, waits for the answer, and has to
leave a pause of at least 100 ms between two conversations. Together with the transmission time and the boiler's
own answer time (up to 400 ms), a controller can do only about three updates per second. A boiler that supports many
values can't be polled all at once.

This component therefore works through the configured values one after another, as follows:

- A **pass** is one scan over all configured values, asking for each one that is due.
- A **sweep** is enough passes for every value to be asked for at least once, including the slowest ones.
- **update_every** decides how often a value is due: `1` means on every pass, `4` on every fourth pass, and so on. It
  is a relative scale, not a number of seconds. How long a pass takes depends on how many entities you configured, so
  configure only what you need.
- Values that change quickly get low numbers (the status exchange, setpoints). Slowly changing values (lifetime
  counters, identification) get high numbers. The defaults range from `1` (fastest) to `8` (slowest) and normally
  don't need changing.
- A write (for example, changing the control setpoint) is sent right away, ahead of the schedule.

For example, with 90 values asked on every pass and three conversations per second, a pass takes about 30 seconds.
A value with `update_every: 8` is then refreshed about every four minutes.

Entities that come from the same request of the boiler share one cadence. For instance, all the boiler status bits
come from the same answer. Their cadence is set with a hub option such as
`control_and_status_information_boiler_status_update_every`, listed in [Update Cadence](#update-cadence). Entities with
their own request have an `update_every` option of their own.

### Transient Errors

Some boilers answer "data not available" for a value a few times in a row before giving a real one, for no obvious
reason. Without any tolerance, the entity would flip between unknown and its value. The `max_data_invalid` option sets
how many consecutive "data not available" answers for the same value are tolerated before the entity becomes
unknown. The default `0` marks it unknown on the first one. Timeouts, framing errors and "unknown data id" answers
are never tolerated.

### Diagnostics

The `sweep_duration` and `pass_duration` sensors report how long the last sweep and the last pass took, which helps
you decide how many entities to configure. The `sweep_had_errors` binary sensor turns on if any value failed or was
rejected during the last sweep, not counting answers tolerated by `max_data_invalid`.

## Data Link

The data link is the part that talks to the boiler on the wire. There are two implementations:

- `esp32_rmt` uses the ESP32 RMT hardware peripheral. The hardware sends and receives a whole frame on its own, so
  other components that briefly disable interrupts (for example Dallas temperature sensors) can't disturb the
  communication. It is the default on every ESP32 variant that has the peripheral.
- `esp_isr` is a software implementation driven by a timer interrupt. It is used on the ESP8266 and on the ESP32
  variants without the RMT peripheral (ESP32-C2 and ESP32-C61).

The right one is chosen automatically, and you should never need to set the `datalink` option. Use it only to force
`esp_isr` if all the RMT channels of your board are already in use by other components. `esp32_rmt` on a board
without the RMT peripheral is a configuration error. With `esp_isr`, other components that disable interrupts for a
long time can cause lost frames, and only one hub is possible on the ESP8266.

## opentherm42 Hub

First, define the hub. All the entities below need it. The `opentherm42_id` option of the platforms is only needed
if you have more than one hub.

```yaml
opentherm42:
  in_pin: GPIOXX
  out_pin: GPIOXX
```

### Configuration Variables

- **in_pin** (**Required**, [Pin](/guides/configuration-types#pin)): The pin of the OpenTherm adapter which is usually
  labeled `out` on the board.

- **out_pin** (**Required**, [Pin](/guides/configuration-types#pin)): The pin of the OpenTherm adapter which is usually
  labeled `in` on the board.

- **id** (*Optional*, [ID](/guides/configuration-types#id)): Manually specify the ID used for code generation. Required
  if you have multiple hubs.

- **controller_member_id_code** (*Optional*, int [0-255], default **0**): This controller's own identity, announced to
  the boiler. A MemberID of 0 means "no specific manufacturer" -- leave it at 0 unless your controller has a
  manufacturer-assigned OpenTherm MemberID. *(OpenTherm spec §5.3.2, ID 2 LB)*

- **controller_product_type** (*Optional*, int [0-255], default **0**): This controller's own product type, as assigned
  by its manufacturer. 0 if not applicable. *(OpenTherm spec §5.3.2, ID 126 HB)*

- **controller_product_version** (*Optional*, int [0-255], default **0**): This controller's own product version, as
  assigned by its manufacturer. 0 if not applicable. *(OpenTherm spec §5.3.2, ID 126 LB)*

- **time_id** (*Optional*, [ID](/guides/configuration-types#id) of a [time](/components/time/)): Keeps the boiler's
  clock (day of week/time, date, year) synced to this time source. *(OpenTherm spec §5.3.4, ID 20/21/22)* Required by
  the `time_synchronized` binary sensor and the `sync_time` button.

- **max_data_invalid** (*Optional*, int, default **0**): Some boilers answer "data not available" for a reading a few
  times in a row before giving a real value, for no obvious reason. This tolerates that many consecutive invalid
  responses to the same reading before actually marking its entity Unknown, instead of flipping back and forth. 0 (the
  default) marks it Unknown on the very first invalid response. *(OpenTherm spec §4.4.1)* See [Transient
  Errors](#transient-errors).

- **datalink** (*Optional*, string, one of `esp32_rmt`, `esp_isr`): How the component talks to the boiler. Leave it
  unset: the best option for your board is chosen automatically. See [Data Link](#data-link).

  controller announces its product type and version (`controller_product_type`, `controller_product_version`). It always
