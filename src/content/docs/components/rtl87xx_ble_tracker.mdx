The `rtl87xx_ble_tracker` component creates a global hub so that you can track Bluetooth Low Energy
devices using your RTL87xx node — the Realtek AmebaD family (RTL8720D/RTL8720DN, such as the
BW16 module; hardware-verified) and the AmebaZ2 family (RTL8720C/RTL8710C, such as the BW15
module; compiles and is CI-covered, but not yet verified on hardware).

This component provides the **BLE scanner** and the listener interface used by
ESPHome's advertisement-based BLE sensor platforms — for example
[BLE RSSI](/components/sensor/ble_rssi/), [BLE Presence](/components/binary_sensor/ble_presence/),
[BLE Scanner](/components/text_sensor/ble_scanner/) and [Xiaomi BLE](/components/sensor/xiaomi_ble/)
— which attach to this tracker automatically.

> [!NOTE]
> The tracker is scan-only and cannot open GATT connections, so
> [`ble_client`](/components/ble_client/) is not available on this platform.
> [`bluetooth_proxy`](/components/bluetooth_proxy/) works in advertisement-only mode — see
> [Platform Support](/components/bluetooth_proxy/#platform-support).

> [!NOTE]
> BLE is available on the **AmebaD** family (RTL8720D/RTL8720DN boards such as `bw16`,
> hardware-verified) and the **AmebaZ2** family (RTL8720C/RTL8710C boards such as `bw15`,
> compile-tested only — selecting one warns that no hardware verification has happened yet).
> The AmebaZ family (RTL8710B) has no BLE radio.

> [!NOTE]
> WiFi and BLE **share the radio** on the RTL8720D; the chip's hardware coexistence arbiter
> time-shares it. The scan `window` / `interval` ratio decides how much airtime BLE scanning
> takes from WiFi while a scan runs. See [Use with a shared radio](#use-with-a-shared-radio)
> below.

```yaml
# Example configuration entry
rtl87xx_ble_tracker:
```

## Configuration variables

- **scan_parameters** (*Optional*): Advanced parameters for configuring the scan behaviour.
  See also [this guide by Texas Instruments](https://dev.ti.com/tirex/explore/content/simplelink_academy_cc2640r2sdk_5_10_02_00/modules/blestack/ble_scan_adv_basic/ble_scan_adv_basic.html#scanning-basics)
  for background reading.

  - **interval** (*Optional*, [Time](/guides/configuration-types#time)): The interval between
    each consecutive scan window. The scanner cycles through the three BLE advertising channels
    at this rate. Defaults to `100ms`, which together with the default `window` gives a 30 %
    duty cycle — the same defaults as the other single-radio LibreTiny trackers. (The Realtek
    GAP reference default of 820 ms is far too slow for device tracking.) A larger interval
    lowers the duty cycle and frees more airtime for WiFi, at the cost of catching fewer
    advertisements.

  - **window** (*Optional*, [Time](/guides/configuration-types#time)): The time the receiver is
    actively listening for packets on a channel during each scan interval. Must be ≤ `interval`.
    Defaults to `30ms`.

  - **duration** (*Optional*, [Time](/guides/configuration-types#time)): The length of each
    complete scan session. When `continuous` is `true` the scanner keeps running and fires
    `on_scan_end` once per `duration` period. Defaults to `5min`.

  - **active** (*Optional*, boolean): When `true` the scanner sends scan-request packets to
    request additional advertisement data (scan response). Defaults to `true`, matching
    [ESP32 BLE Tracker](/components/esp32_ble_tracker/).

    > [!NOTE]
    > As on ESP32 (where ESP-IDF performs the merge), an advertisement and its scan
    > response are combined into a single result, so automations and sensor platforms
    > receive one merged frame containing both payloads — this is where device names come from.
    > The merge is best-effort: a scannable advertisement is held briefly (up to 300 ms) waiting
    > for its scan response, and a device that does not answer the scan request is delivered
    > unmerged (without a name) after that timeout.

  - **continuous** (*Optional*, boolean): When `true` the scanner runs permanently and is
    re-established automatically if the controller drops the scan. When `false` a scan runs
    once for `duration` after `rtl87xx_ble_tracker.start_scan`; nothing scans on boot unless
    an automation starts it. Defaults to `true`.

- **id** (*Optional*, [ID](/guides/configuration-types#id)): Manually specify the ID used to
  reference this component in lambdas.

Automations:

- **on_ble_advertise** (*Optional*, [Automation](/automations)): An automation to perform
  when a BLE advertising packet is received. Optionally filtered to a list of `mac_address`es.
  See [`on_ble_advertise` Trigger](#rtl87xx_ble_tracker-on_ble_advertise).
- **on_ble_manufacturer_data_advertise** (*Optional*, [Automation](/automations)): An automation
  to perform when a BLE advertising packet with matching manufacturer data is received.
  See [`on_ble_manufacturer_data_advertise` Trigger](#rtl87xx_ble_tracker-on_ble_manufacturer_data_advertise).
- **on_ble_service_data_advertise** (*Optional*, [Automation](/automations)): An automation to
  perform when a BLE advertising packet with service data for `service_uuid` is received.
  See [`on_ble_service_data_advertise` Trigger](#rtl87xx_ble_tracker-on_ble_service_data_advertise).
- **on_scan_end** (*Optional*, [Automation](/automations)): An automation to perform when a scan
  session ends (its `duration` elapsed, or `stop_scan` was called). Fires on every `duration`
  period when `continuous` is `true`. See [`on_scan_end` Trigger](#rtl87xx_ble_tracker-on_scan_end).

## RTL87xx BLE Tracker Automation

<span id="rtl87xx_ble_tracker-on_ble_advertise"></span>

### `on_ble_advertise` Trigger

This automation will be triggered when a BLE advertising packet is received. A variable `x` of
type <APIClass text="ble_device_base::ESPBTDevice" path="ble_device_base::ESPBTDevice" /> is
passed to the automation for use in lambdas.

```yaml
rtl87xx_ble_tracker:
  on_ble_advertise:
    # Optional multi-device filter; omit mac_address to fire on every advertisement.
    - mac_address:
        - XX:XX:XX:XX:XX:XX
        - XX:XX:XX:XX:XX:XX
      then:
        - lambda: |-
            ESP_LOGD("ble_adv", "Advertisement from %s (RSSI %d), name '%s'",
                     x.address_str().c_str(), x.get_rssi(), x.get_name().c_str());
```

Add an optional `mac_address` filter (a list) to restrict the automation to specific devices, and
use the device accessors — `x.get_service_uuids()`, `x.get_service_datas()`,
`x.get_manufacturer_datas()` — to inspect the advertisement payload.

#### Configuration variables

- **mac_address** (*Optional*, list of MAC Address): The MAC address to filter for this automation.
- See [Automation](/automations).

<span id="rtl87xx_ble_tracker-on_ble_manufacturer_data_advertise"></span>

### `on_ble_manufacturer_data_advertise` Trigger

This automation will be triggered when a BLE advertising packet with manufacturer-specific data
is received. A variable `x` of type `std::vector<uint8_t>` is passed to the automation for use
in lambdas.

```yaml
rtl87xx_ble_tracker:
  on_ble_manufacturer_data_advertise:
    - mac_address: XX:XX:XX:XX:XX:XX
      manufacturer_id: 0590
      then:
        - lambda: |-
            ESP_LOGD("ble_man_data", "Manufacturer data of length %i", x.size());
```

#### Configuration variables

- **mac_address** (*Optional*, MAC Address): The MAC address to filter for this automation.
- **manufacturer_id** (**Required**, string): 16-bit, 32-bit, or 128-bit BLE manufacturer ID in hex.
- See [Automation](/automations).

<span id="rtl87xx_ble_tracker-on_ble_service_data_advertise"></span>

### `on_ble_service_data_advertise` Trigger

This automation will be triggered when a BLE advertising packet with service data is received. A
variable `x` of type `std::vector<uint8_t>` is passed to the automation for use in lambdas.

```yaml
rtl87xx_ble_tracker:
  on_ble_service_data_advertise:
    - mac_address: XX:XX:XX:XX:XX:XX
      service_uuid: FCD2
      then:
        - lambda: |-
            ESP_LOGD("ble_svc_data", "Service data of length %i", x.size());
```

#### Configuration variables

- **mac_address** (*Optional*, MAC Address): The MAC address to filter for this automation.
- **service_uuid** (**Required**, string): 16-bit, 32-bit, or 128-bit BLE service UUID in hex
  (e.g. `FCD2` for BTHome v2, `181A` for Environmental Sensing).
- See [Automation](/automations).

<span id="rtl87xx_ble_tracker-on_scan_end"></span>

### `on_scan_end` Trigger

This automation will be triggered when a Bluetooth scan session has completed. When `continuous`
is `true` this fires once per `duration` period while the scan keeps running.

```yaml
rtl87xx_ble_tracker:
  on_scan_end:
    - then:
        - lambda: |-
            ESP_LOGD("ble_auto", "The scan has ended!");
```

#### Configuration variables

- None.
- See [Automation](/automations).

### `rtl87xx_ble_tracker.start_scan` Action

Start a Bluetooth scan. The optional [templatable](/automations/templates#config-templatable)
`continuous` overrides the scan mode until the next `start_scan` or `stop_scan` (the
YAML-configured value itself is untouched); without it the mode configured under
`scan_parameters` is restored (a previous `stop_scan` does not stick as "one-shot"). This
differs from `esp32_ble_tracker.start_scan`, where an omitted `continuous` always forces a
one-shot scan. Invoked while a scan is already running, a mode switch re-anchors the running
scan's `duration` window instead of restarting the radio; a same-mode call is a no-op.

```yaml
rtl87xx_ble_tracker:
  scan_parameters:
    continuous: false

on_...:
  - rtl87xx_ble_tracker.start_scan:
      continuous: true
```

#### Configuration variables

- **continuous** (*Optional*, [templatable](/automations/templates#config-templatable), boolean):
  Override the scan mode until the next `start_scan` or `stop_scan` (the YAML-configured value
  itself is untouched). When omitted, the mode configured under `scan_parameters` is
  restored — a previous `stop_scan` does not stick as "one-shot".

### `rtl87xx_ble_tracker.stop_scan` Action

Stop the running Bluetooth scan. Accepts the bare-id shorthand
(`rtl87xx_ble_tracker.stop_scan: my_tracker`). It can be restarted with
`rtl87xx_ble_tracker.start_scan`.

```yaml
on_...:
  - rtl87xx_ble_tracker.stop_scan:
```

## With BLE sensors

Sensor platforms attach to the tracker automatically (identical to ESP32):

```yaml
rtl87xx_ble_tracker:

sensor:
  - platform: xiaomi_lywsd03mmc
    mac_address: XX:XX:XX:XX:XX:XX
    bindkey: "00112233445566778899aabbccddeeff"
    temperature:
      name: "Temperature"
    humidity:
      name: "Humidity"
  - platform: ble_rssi
    mac_address: XX:XX:XX:XX:XX:XX
    name: "BLE Beacon RSSI"
```

## Use with a shared radio

WiFi and BLE share one radio on the RTL8720D; the hardware coexistence arbiter time-shares it,
so a running scan takes airtime from WiFi rather than CPU time. To keep the radio free whenever
nobody is listening, the scan actions can time-share instead — scan only while Home Assistant is
connected:

```yaml
rtl87xx_ble_tracker:
  scan_parameters:
    continuous: false   # do not start on boot

api:
  on_client_connected:
    - rtl87xx_ble_tracker.start_scan:
        continuous: true
  on_client_disconnected:
    # fires for EVERY departing client (log viewer, CLI) — only stop
    # scanning when the LAST client is gone (HA no longer connected)
    - if:
        condition:
          not:
            api.connected:
        then:
          - rtl87xx_ble_tracker.stop_scan:
```

The scan `window` / `interval` ratio decides how the radio is split between BLE scanning and
WiFi while a scan runs. Keep `window: 30ms` and choose the `interval`:

- `interval: 100ms` → **30 / 70** BLE / WiFi — the default
- `interval: 200ms` → **15 / 85** BLE / WiFi — catches fewer advertisements, but leaves more of
  the radio for WiFi

Setting `active: false` is a second lever: the scanner no longer sends scan requests to request
more data after receiving an advertising packet, keeping the radio cost of each window minimal.
BTHome/ATC-style sensors that broadcast all their data in the advertisement don't need active
scanning.

Scanning is paused automatically while an OTA update is in flight, so the transfer gets the
whole radio; a failed or aborted update restores the previous scan state.
