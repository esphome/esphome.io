The `tormatic` cover platform allows you to control Tormatic and Novoferm
garage door drives manufactured in 2016 onwards. The following models should
be supported:

* Tormatic Black 600, Black 800, Black 1000
* Novoferm Novomatic 423
* Novoferm Novomatic 563 S
* Novoferm Novoport IV

> [!NOTE]
> This component was written against a Novoferm 423. It has been successfully
> tested with Novoferm 423 and Tormatic Black 600, so compatibility with other
> models is currently not guaranteed. Please update this documentation if you
> confirm this to work on other models as well.
>
> The vendor's cloud-based remote is not known to perform model or feature
> detection, so it's assumed that the protocol is the same across all models.

As the communication with the garage door drive is done using UART, you need to
have an [UART bus](/components/uart) in your configuration with the `rx_pin`
connected to the unit's USB D- line and the `tx_pin` connected to the USB's D+
line. The baud rate should be set to 9600. See
[Connecting to the unit](#connecting-to-the-unit) for detailed instructions.

```yaml
# Example configuration entry
cover:
  - platform: tormatic
    device_class: garage
    name: Novoferm 423
```

## Connecting to the unit

The garage door drive ('unit') contains a female USB Type B port that does
**not** speak the USB protocol. It is not a conventional USB port, though it
supplies 5V between the usual USB Vcc and ground pins and can be used to feed an
ESP32 board.

The D+ and D- terminals are used as a 9600/8N1 UART pair **with 5V logic levels
(!)**. The unit pulls the USB's D- (white) line high and uses it to transmit
data. It receives data on the D+ (green) line, meaning **the ESP should
transmit on D+ and receive on D-**.

To build the cable, you'll need:

* An ESP32 board, ideally an S2 Mini (see [below](#esp32-s2-mini-over-usb-c))
* A sacrificial USB cable with a Type B plug on one end
* A bidirectional MOSFET level shifter module (2 channels or more)
* A short USB-C (or other, matching your board) cable to connect the shifter's
  low-voltage side to the ESP

### Level shifter

All current ESP family devices expect 3.3V logic levels, so a level shifter is
needed on both data lines for this to work correctly. Experiments with
connecting an ESP32 S2's GPIO hardware directly to these pins yielded strange
results; the ESP runs hot, doesn't connect to WiFi and the ESP's 3.3V tx logic
level is slightly underpowered, so the unit doesn't receive the ESP's messages
correctly most of the time.

ESP as follows:

### ESP32 S2 Mini over USB-C

On an S2 Mini, the USB-C connector's D- and D+ lines are routed directly to
GPIO19 and GPIO20, since there is no separate in-line USB chip. This allows
feeding the shifted UART signal straight into the ESP's USB-C port, making the
S2 an ideal device for this purpose; it keeps the cable simple and compact. Only
a single header pin needs to be soldered to the PCB to supply 3.3V to the level
shifter's LV pin. It can be bent 90 degrees to sit parallel to the PCB, keeping
a low profile.

<Figure
  src={s2Mini3v3Img}
  alt="An ESP32 S2 Mini with the modified USB-C cable plugged in and a red jumper wire attached to a single header pin"
  caption="The finished cable plugged into the S2 Mini's USB-C port. The red jumper supplies 3.3V to the level shifter's LV pin."
  layout="constrained"
/>

Since ESPHome 2024.5, ESP-IDF claims the S2's USB peripheral during startup,
which breaks UART on GPIO19/20. Disable the USB peripheral to release the pins:

```yaml
esp32:
  board: lolin_s2_mini
  framework:
    type: esp-idf
    sdkconfig_options:
      CONFIG_USB_OTG_SUPPORTED: "n"
      CONFIG_TINYUSB: "n"

uart:
  rx_pin: GPIO19 # USB D-
  tx_pin: GPIO20 # USB D+
  baud_rate: 9600
```

> [!NOTE]
> This disables the board's native USB functionality, like serial logging over
> USB. Flashing over USB still works through the ROM bootloader (hold the `0`
> button while pressing `RST`), and OTA updates are unaffected.

If a compact cable is not a concern, any other free pair of GPIOs works with the
level shifter wired the same way, without the `sdkconfig_options` overrides.

## Configuration variables

* **name** (**Required**, string): The name of the cover.
* **open_duration** (*Optional*, [Time](/guides/configuration-types/#time)): The amount of time the
  gate is expected to need to go from a fully closed to opened state. Defaults
  to `15s`. Used to interpolate the position value published to Home Assistant
  during gate movements, and for stopping the gate at a specific requested
  position. This value is automatically recalibrated after an uninterrupted
  closed -> opened movement.

* **close_duration** (*Optional*, [Time](/guides/configuration-types/#time)): The opposite of
  `open_duration`. Defaults to `22s`.

* All other options from [Cover](/components/cover/#config-cover).

## Known Issues

* Pausing an action twice (e.g. open - pause - open - pause) will result in the
   unit incorrectly remaining in 'opening' status for exactly 60 seconds. This
   is difficult to work around without making the protocol completely
   client-side authoritative, but this would mean we can no longer detect gate
   movements initiated by the physical button or an RF remote. An annoying but
   acceptable defect.

* The position updates during gate movements are time-based approximations and
   don't account for acceleration and grace movements near the start and end of
   the action. The unit itself doesn't provide accurate position information.
