The `rs485_frame` text_sensor platform exposes a single hub diagnostic: the
type of the most recently validated frame, as a 4-character hex string (e.g.
`"0083"`, no separator). It requires the [RS485 Frame](/components/rs485_frame/)
hub to be configured.

This tracks **every** validated frame on the bus, not only frames matched by an
`on_frame:` trigger — so it reflects the last frame type seen on the wire,
whatever it was.

This is useful for cataloging frame types on an unknown bus during the
discovery workflow. For user payload decoding, use [`on_frame:` on the
hub](/components/rs485_frame/#configuration-variables) — that handles every
text-decoding case from a single ASCII frame through Hayward AquaLogic's
blink-bit-and-degree-symbol display encoding.

## Configuration variables

- **rs485_frame_id** (**Required**, [ID](/guides/configuration-types#id)): The ID of the `rs485_frame` hub.
- **update_interval** (*Optional*, [Time](/guides/configuration-types#time)): How often to
  check the hub's last frame type. Defaults to `60s`: on a live bus the frame type changes
  on nearly every frame (Hayward interleaves keep-alive, LED, and display frames; a Jandy
  master polls several devices in turn), so checking more often mostly adds API traffic.

All other options from [Text Sensor](/components/text_sensor/#base-text-sensor-configuration).
The platform defaults `entity_category: diagnostic` so Home Assistant groups
this with the device's other diagnostic entities; override in YAML if you want
to surface it elsewhere.

The sensor publishes only when the frame type differs from its last published value, at
most once per `update_interval`, so a steady-state bus produces no API traffic.

For bring-up or reverse engineering, lower `update_interval` (for example `100ms` to `1s`) to see
frame-type changes sooner. Values down to `1ms` are accepted (ESPHome raises `0ms` to `1ms`); each
step down trades more API traffic for fresher readings.

At any interval, the sensor is a sample, not a record: it holds only the most recent frame type, so
frames that arrive between two checks overwrite each other and are never published. To see every
frame, use the hub's own tools:

- [`dump_frames: true`](/components/rs485_frame/#configuration-variables) logs every validated RX
  frame and every TX frame at DEBUG level, and is cheap enough to leave on while you work.
- [`sniffer_stats:`](/components/rs485_frame/#optional-enable-sniffer-stats) logs a per-frame-type
  table of counts and timings on a fixed interval.
- [`frame_trace:`](/components/rs485_frame/#frame-trace) keeps a ring buffer of recent RX and TX
  frames, including ones that failed validation, and dumps it to the log on demand.
- [`on_frame:`](/components/rs485_frame/#configuration-variables) runs your automation for every
  matching frame.

## Example

```yaml
text_sensor:
  - platform: rs485_frame
    rs485_frame_id: pool
    name: "Last Frame Type"
```

When a frame with payload starting `0x01 0x03 ...` is validated, the sensor
publishes the state `"0103"`. The first two payload bytes are shown; longer
frame_type prefixes still match in your `on_frame:` handlers but the diagnostic
shows only the leading two bytes (which is the conventional frame type width).
