The `storage_worker` component provides non-blocking file copy and move operations on top of the
[storage](/components/storage/) interface. Storage operations are normally blocking, which means a large file
transfer can make the device temporarily unresponsive to sensor updates and API requests (see
`max_blocking_transfer_size` on the `storage` component). `storage_worker` addresses this for copy/move by
processing transfers in small chunks over time instead of doing the whole transfer in a single call.

You do not need to add `storage:` separately; `storage_worker` depends on it and loads it automatically.

> [!WARNING]
> The storage interface, including `storage_worker`, is **experimental**. Breaking changes may occur in future
> ESPHome releases as the component evolves.

```yaml
# Example configuration entry
storage_worker:
```

## Configuration variables

- **id** (*Optional*, [ID](/guides/configuration-types#id)): Manually specify the ID for this component.
- **task_stack_size** (*Optional*, int): Stack size, in bytes, for the background worker task on platforms that
  have one (currently ESP32). Needs headroom for FATFS long-filename handling and NFS/lwIP transfers. Must be
  between 4096 and 32768. Defaults to `8192`.
- **task_priority** (*Optional*, int): FreeRTOS priority for the background worker task. Should be above idle and
  below networking-related tasks. Must be between 1 and 23. Defaults to `1`.
- **max_pending** (*Optional*, int): Maximum number of copy/move requests that can be queued at once. Must be
  between 1 and 16. Defaults to `4`. Submitting a request while the queue is full is rejected immediately.

## How it works

Every storage driver reports whether it's safe to access from a background task (this is the driver's
capability, not something you configure here). When both the source and destination of a transfer report this,
and the platform has a background task available, `storage_worker` runs the transfer on that task, off the main
loop entirely. Otherwise — including on every platform without a background task — it falls back to processing
one small chunk of the transfer per main loop iteration, the same way many other ESPHome components spread work
out over time. Either way, the request completes the same way from the caller's point of view: a callback is
invoked once, always from the main loop, when the transfer finishes or fails.

If a storage device is removed (e.g. a USB drive unplugged, an SD card removed) while a transfer involving it is
queued or in progress, the transfer is stopped and completed with an error rather than left to fail unpredictably.

## C++ API

This section is for component developers who want to trigger a copy or move from custom components or lambdas.

```cpp
#include "esphome/components/storage_worker/storage_worker.h"

// storage_worker::CompletionCallback is std::function<void(storage::StorageError)>
esphome::storage_worker::global_storage_worker->async_copy(
    src_storage, "/sd/source.txt", dst_storage, "/usb/dest.txt", [](storage::StorageError result) {
      if (result == storage::StorageError::OK) {
        // done
      }
    });
```

`async_move()` has the same signature. Both return a `storage::StorageError` immediately: `StorageError::OK` if
the request was accepted (the callback will be invoked later), or an error — most commonly
`StorageError::NOT_READY` if the request queue is full — if it was rejected outright, in which case the callback
is **not** invoked.
