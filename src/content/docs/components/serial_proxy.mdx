The `serial_proxy` component exposes a physical UART serial port on your ESPHome device to API clients
(such as Home Assistant) via the [Native API](/components/api/). This allows an API client to send and
receive data directly to and from a serial device connected to the ESP, effectively creating a
network-attached serial port.

The component requires the [Native API](/components/api/) and [UART](/components/uart/) components.

Multiple `serial_proxy` instances may be configured on a single device, each attached to a different UART.

```yaml
# Example configuration entry
serial_proxy:
  - id: serial_proxy_1
    uart_id: serial_1
    name: My Serial Device
    port_type: TTL
```

## Configuration variables

- **id** (*Optional*, [ID](/guides/configuration-types#id)): Manually specify the ID to use for code generation.
- **name** (**Required**, string): A human-readable name for this serial port, used to identify it to API clients.
- **uart_id** (**Required**, [ID](/guides/configuration-types#id)): The ID of the [UART](/components/uart/) component
  this proxy is attached to.
- **port_type** (**Required**, string): The electrical type of the serial port. One of:
  - `TTL`: Standard TTL logic-level UART (3.3V or 5V). Typically used for direct connections to most microcontrollers.
  - `RS232`: RS-232 standard serial port (typically ±12V levels via an appropriate line-driver IC). Typically used for PC-style serial connections, often with a DB9-type connector.
  - `RS485`: RS-485 differential serial bus. Typically used for industrial/multi-drop serial networks.
  - `USB_SERIAL`: A serial device attached through a USB bridge. Requires `uart_id` to refer to a
    [USB UART](/components/usb_uart/) channel.
- **rts_pin** (*Optional*, [Pin](/guides/configuration-types#pin)): GPIO pin to use as the RTS (Request to Send)
  modem control output. The state of this pin may be controlled by the API client at runtime.
- **dtr_pin** (*Optional*, [Pin](/guides/configuration-types#pin)): GPIO pin to use as the DTR (Data Terminal Ready)
  modem control output. The state of this pin may be controlled by the API client at runtime.
- **identity** (*Optional*): The identity of the device behind the port, reported to API clients. Each string value
  is a string or a [lambda](/automations/templates#config-lambda), evaluated once at setup. At least one of
  `manufacturer`, `product`, `serial_number`, or `vid` is required.
  Not allowed when `uart_id` refers to a [USB UART](/components/usb_uart/) channel, as the identity is then read
  from the USB descriptors.
  - **manufacturer** (*Optional*, string): The manufacturer of the device.
  - **product** (*Optional*, string): The product name of the device.
  - **serial_number** (*Optional*, string): The serial number of the device.
  - **vid** (*Optional*, int): The USB vendor ID of the device. Requires `pid`.
  - **pid** (*Optional*, int): The USB product ID of the device. Requires `vid`.
  - **bcd_device** (*Optional*, int): The USB device release number. Defaults to `0`.
  - **interface_number** (*Optional*, int): The USB interface number the serial port is on. Defaults to `0`.

  The USB fields let a device that is not attached over USB report itself as a USB device. For example, a
  USB serial adapter built onto a board and wired to a UART. If the values match the real USB descriptors, API
  clients see the same device whether it is plugged in over USB or attached to this port.

## How It Works

When an API client connects, it can:

- **Send data** to the serial device by writing bytes through the API.
- **Receive data** from the serial device — data arriving on the UART is forwarded to connected API clients automatically each loop iteration (up to 256 bytes at a time).
- **Reconfigure the UART** at runtime — the API client may change the baud rate, data bits, stop bits, and parity without reflashing firmware.
- **Control modem pins** — if `rts_pin` or `dtr_pin` are configured, the API client can set their states at runtime.
- **Identify devices** — the API client can read the identity of the device behind each port. The identity comes
  from `identity`, or from the USB descriptors if `uart_id` refers to a [USB UART](/components/usb_uart/) channel.
  For USB, the API client is notified when a device is attached or removed.

## Full Example

```yaml
# Three serial proxies on separate UARTs
uart:
  - id: device_uart
    tx_pin: GPIO4
    rx_pin: GPIO5
    baud_rate: 9600

  - id: rs485_uart
    tx_pin: GPIO16
    rx_pin: GPIO17
    baud_rate: 19200

  - id: zigbee_uart
    tx_pin: GPIO21
    rx_pin: GPIO22
    baud_rate: 460800

api:

serial_proxy:
  - id: device_serial
    uart_id: device_uart
    name: TTL Device
    port_type: TTL

  - id: rs485_serial
    uart_id: rs485_uart
    name: RS-485 Bus
    port_type: RS485
    rts_pin: GPIO18
    identity:
      manufacturer: Acme
      product: RS-485 Adapter
      serial_number: !lambda return str_upper_case(get_mac_address());

  - id: zigbee_serial
    uart_id: zigbee_uart
    name: Zigbee
    port_type: TTL
    identity:
      manufacturer: Nabu Casa
      product: ZBT-2
      serial_number: 10B41DE58F10
      vid: 0x303A
      pid: 0x4001
      bcd_device: 0x0101
```
