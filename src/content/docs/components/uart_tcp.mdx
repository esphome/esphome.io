This component allows bytes to be transferred between a hardware [UART bus](/components/uart/) and a TCP socket.
Data is copied unchanged in both directions.

The component can connect to a remote host (`role: client`) or listen for one incoming connection (`role: server`).
Only one TCP connection is open at a time. When `role` is `server`, a new client is accepted only after the current
connection is closed.

> [!WARNING]
> Without `encryption`, the connection is plain TCP with no encryption and no authentication; only use it on a
> trusted network. `allowed_ips` filters by address but does not authenticate the peer. If it is omitted, any host
> that can reach the port is accepted, and the first client to connect is the one that is served. With
> `encryption`, a host without the key still holds the server until its handshake fails or times out.

> [!NOTE]
> While no connection is open or, with `encryption`, until the handshake has succeeded, bytes from the UART are
> discarded; a fast peer is throttled by TCP flow control instead of blocking the device.

> [!NOTE]
> Baud rate, data bits, parity and stop bits are set on the UART bus. They are not options of this component.

This is not Modbus TCP. Without `encryption`, the bytes on the socket are the UART bytes, unchanged.

The examples assume a [UART bus](/components/uart/) with the id `uart_bus` is configured.

## Client

```yaml
# Example configuration entry
uart_tcp:
  - id: uart_tcp_1
    uart_id: uart_bus
    host: 192.0.2.20
    port: 8899
```

## Server

```yaml
# Example configuration entry
uart_tcp:
  - id: uart_tcp_1
    uart_id: uart_bus
    role: server
    port: 8899
```

## Configuration Variables

- **id** (*Optional*, [ID](/guides/configuration-types#id)): Manually specify the ID used for code generation.
- **uart_id** (**Required**, [ID](/guides/configuration-types#id)): The [UART bus](/components/uart/) to use. This
  component needs the UART for itself: another component with the same `uart_id`, or `dummy_receiver` in the UART's
  [debug](/components/uart/#debugging) option, is rejected. A `uart.write` action or a lambda that uses the UART is
  not detected, so avoid them.
- **role** (*Optional*, string): `client` or `server`. Defaults to `client`.
- **host** (**Required** when `role` is `client`, string): The host to connect to. An IPv4 address or a hostname.
  IPv6 is not supported.
  This option cannot be used when `role` is `server`.
- **port** (**Required**, int): The TCP port to connect to, or to listen on. When `role` is `server`, a second
  `uart_tcp` or `tcp_uart` server on the same port is rejected.
- **allowed_ips** (*Optional* when `role` is `server`, list): IPv4 addresses that may connect. A plain
  address is one host. A network is written in CIDR form, for example `192.0.2.0/24`. At most 255 entries. If
  the option is omitted, every address may connect. A rejected client is closed immediately and logged as a
  warning at most once every 5 seconds; an IPv6 client is rejected unless it carries an IPv4 mapped address, as
  on a dual stack network. This option cannot be used when `role` is `client`.
- **timeout** (*Optional*, [Time](/guides/configuration-types#time)): Close the connection when no byte has
  been sent or received for this long. Time is counted from the last byte, or from when the connection opened.
  `0s` turns the timeout off and leaves the connection open; any other value must be at least the main loop
  interval ([`loop_interval`](/components/esphome#configuration-variables), `16ms` by default). Defaults to `0s`.
  A UART that cannot take more bytes also counts as traffic, so the connection stays up while bytes are waiting for
  the bus even if the peer has stopped. On a client, the next connection waits for `reconnect_interval`. On a
  server, the next client is accepted as soon as this connection is closed.
- **encryption** (*Optional*): Encrypt the connection with a key that both ends hold. The other end must be an
  ESPHome [TCP UART](/components/tcp_uart/) or UART TCP with the same key, so other programs cannot connect. A
  connection whose handshake fails or does not finish within 60 seconds is closed and logged. After a failed
  handshake, a client waits `reconnect_interval` before it tries again, then twice as long after each further
  failure, up to 5 minutes; each wait varies at random by up to 20%. A successful handshake starts over at
  `reconnect_interval`.
  - **key** (**Required**, string): A base64 encoded 32-byte key, for example from `openssl rand -base64 32`. It must
    differ from the [API](/components/api/) and [OTA](/components/ota/esphome/) encryption keys, because the other
    device holds this key too; a configuration with an equal key is rejected. A key the API gets at runtime is not
    checked.
- **reconnect_interval** (*Optional*, [Time](/guides/configuration-types#time)): The time to wait before trying
  again after a failure. An unanswered connection attempt is given up after `reconnect_interval` or 10 seconds,
  whichever is longer. Defaults to `5s`.
- **connected** (*Optional*): A binary sensor that reports whether the TCP connection is established, with
  `encryption` once the handshake has succeeded. All options
  from [Binary Sensor](/components/binary_sensor#config-binary_sensor) are supported.
- **disconnects** (*Optional*): A sensor that counts how many times an open connection, with `encryption` one whose
  handshake succeeded, has closed. It starts at
  `0` on boot and does not increase again while the connection stays down. All options from
  [Sensor](/components/sensor#config-sensor) are supported.

## Zigbee Coordinator

This setup has not been tested with this component. Zigbee2MQTT can use a server of this component instead
of a serial port on the machine that runs it: in its `configuration.yaml`, set `serial.port` to
`tcp://<device ip>:<port>` and `baudrate` to the UART's baud rate. Zigbee2MQTT must be the only TCP client.
A stick on an ESP32 with USB host can be exposed the same way through [USB Host UART](/components/usb_uart/).

> [!NOTE]
> [Ethernet](/components/ethernet/) is recommended. A coordinator drops bytes more easily on Wi-Fi than on a
> cable, and Zigbee2MQTT does not tolerate that. If Wi-Fi is the only network, do not also enable
> `bluetooth_proxy`, `esp32_ble_tracker` or `esp32_ble` on this device. They share the radio with Wi-Fi.
